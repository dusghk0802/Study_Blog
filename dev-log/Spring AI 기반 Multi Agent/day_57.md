# 57일차

## 미니프로젝트 인기순 상영 시간표 배분 및 극장 시간표 화면 개선

📌 학습일 : 2026.10.03

📌 학습 내용 : Greedy Scheduling, Quota, Deterministic Seed, Idempotency, Foreign Key Constraint, Safe Update Mode, Lock Wait Timeout, Batch Delete, Stored Procedure, Component Reuse, CSS Custom Property, npm install

#### 1. 모든 상영관이 같은 영화로 채워진 문제

- 극장 화면에서 1관~10관이 **전부 오디세이**로 나오는 문제 발생
- 원인 : 테스트로 개봉일을 `NULL`로 지운 상태에서 서버가 실행되어, 라인업에 **개봉일이 고정된 오디세이 1편만** 들어간 채 시간표가 생성됨
- 개봉일은 나중에 복구됐지만, 시간표 생성 코드는 **이미 있는 회차를 건너뛰는 방식**이라 잘못 만들어진 시간표가 그대로 남아 있었음
- → 시간표는 데이터를 고쳐도 스스로 다시 만들지 않으므로, **규칙이나 데이터가 바뀌면 기존 시간표를 지우고 다시 생성**해야 함

---

#### 2. 인기 순위별 회차 배분 규칙

- 인기 있는 영화는 여러 관에서 더 많이 상영하도록 시간표 규칙을 새로 정함

| 조건 | 내용 |
| --- | --- |
| 라인업 | 그날까지 개봉한 영화 중 **인기순 10편** |
| 기본 배정 | n위 영화가 **n관의 첫 회차**를 차지 (모든 영화가 최소 1개 관) |
| 하루 최대 회차 | 1위 **12회**, 2위 **10회**, 3~5위 **7회**, 6~10위 **3회** |
| 시간 제한 | 마지막 회차는 다음 날 **새벽 3시 전에 종료** |
| 겹침 방지 | 같은 관은 이전 회차 **종료 + 청소 20분 뒤**에만 시작 |

- 배치 방식 : 순위 순서대로 한 회차씩 돌아가며 **가장 빨리 비는 관**에 다음 회차를 넣는 방식 (탐욕적 배치)
  - 정한 횟수를 다 채우거나, 새벽 3시 전에 끝낼 관이 없으면 그 영화는 배치 종료
  - 한 관에서 오전에는 A 영화, 오후에는 B 영화처럼 **여러 영화가 번갈아 상영**됨
- 처음에는 계획 세우기와 저장을 나눠 메서드가 4개였지만, **계획하면서 바로 저장**하도록 합쳐 `scheduleDay()` 하나로 줄임

#### 3. 모든 팀원이 같은 시간표를 보도록 설계

- 인기 순위를 DB 누적관객수로 정하면, 팀원마다 테스트 예매로 숫자가 달라져 **시간표가 달라질 수 있음**
- → 순위를 **설정값 `tmdb.audience-seeds`** 기준으로 정해 설정 파일이 같으면 항상 같은 결과가 나오도록 함

| 시간표를 정하는 값 | 기준 |
| --- | --- |
| 인기 순위 | 설정값 누적관객수 → 개봉일 최신 → TMDB 번호 |
| 첫 회차 시간 | DB 번호가 아닌 **카카오 장소 ID** 해시 |
| 배치 순서 | 순위 → 관 번호 순서로 고정 (무작위 없음) |

- **극장·날짜 단위로 이미 회차가 있으면 그날은 통째로 건너뜀**
  - 같은 날 다시 실행하면 0건, 다음 날 실행하면 새로 추가된 7일째만 생성
  - 극장 단위 `@Transactional`이라 중간에 실패하면 그 극장은 통째로 취소되어 일부만 남지 않음

#### 4. 기존 시간표 삭제 과정

- 시간표를 지우려 했지만 **외래 키(Foreign Key)** 로 여러 테이블이 연결되어 있어 바로 지울 수 없었음

| 연결된 테이블 | 개수 | 의미 |
| --- | --- | --- |
| `showtime_seats` | 5,425,080 | 회차별 좌석 |
| `reservations` | 1 | 예매 (결제·티켓·예매 좌석과 다시 연결) |
| `booking_request_groups` | 1 | 스마트예매 요청 (선호 극장·좌석과 다시 연결) |
| `waiting_queues` | 0 | 대기열 |

- `information_schema.KEY_COLUMN_USAGE`로 **어떤 테이블이 어떤 테이블을 가리키는지** 조회해 삭제 순서를 정함
- 삭제 순서 : **좌석 → 예매에 딸린 데이터 → 예매 → 스마트예매 요청에 딸린 데이터 → 요청 → 시간표** (가리키는 쪽을 먼저 삭제)
- 좌석이 542만 개라 한 번에 지우면 연결이 끊겨서 `LIMIT 100000`으로 **나눠서 삭제**하고, 0개가 될 때까지 반복하는 **저장 프로시저**로 자동화
- 팀원도 같은 과정을 거쳐야 하므로 **실행할 SQL과 Workbench 설정, 에러 대처 방법**을 한 번에 정리해 공지

#### 5. 극장 화면 시간표 개선

- **인기순 정렬** : 팀원이 만든 조회 서비스(`ShowtimeQueryService`)는 수정하지 않고, 프론트에서 메인 차트(`/api/main`)의 순위를 가져와 영화 목록을 정렬
  - 순위를 정하는 데만 쓰고 **개봉일·누적관객수는 화면에 표시하지 않음**
- **예매 버튼 위치** : 목록 맨 아래에 있던 버튼을 여러 방식(바로 예매, 하단 고정 바, 말풍선)과 비교한 뒤, **선택한 시간 카드 안**에 일반·스마트 버튼을 넣기로 결정
  - 기존 시간 카드는 그 자체가 `<button>`이라 **버튼 안에 버튼을 넣을 수 없어서**, 선택한 카드만 같은 모양의 `<div>`로 그림
  - 선택 전·후 카드에 같은 배치 규칙과 **고정 높이(100px)** 를 적용해 선택해도 크기가 변하지 않음
- **표시 정리** : 공용 카드 대신 극장 화면 전용 카드를 그려 날짜, 최대 연속 좌석 문구, `익일` 표시를 빼고 **관·시간·좌석 수**만 표시
- **레이아웃 결정** : 포스터 높이는 고정인데 시간 카드는 1~2줄로 바뀌어 정렬이 맞지 않음 → 4가지 후보를 비교한 뒤 **시간 카드 한 줄 + 옆으로 넘기기**로 결정
  - 메인 화면에서 쓰는 공용 컴포넌트 `HorizontalRail`을 **수정하지 않고 가져다 쓰기만** 함
  - 화살표 위치는 공용 컴포넌트가 제공하는 CSS 변수 `--rail-arrow-top`을 극장 화면 CSS에서만 바꿔 조정
  - 포스터 높이를 **제목 줄(26) + 간격(12) + 카드(100) = 138px**로 맞춰 위·아래 정렬

#### 6. 협업 중 확인한 내용

- **팀원 코드와 충돌** : 팀원이 시간표 설정 파일을 바꿔 `seedTheater()`가 **상영관 수와 회차 수를 묶은 결과**를 돌려줘야 했는데, 전체 교체한 코드가 숫자 하나만 돌려줘 컴파일 에러 발생 → `SeedResult` record를 추가해 해결
  - 설정 파일을 보니 시간표 생성 뒤 **좌석도 자동으로 다시 생성**되는 구조였음
  - 전체 교체 전에는 **Compare with Branch → main**으로 팀원 변경 사항을 먼저 확인해야 함
- **`npm install`** : 팀원이 QR 코드 라이브러리(`qrcode.react`)를 추가해 `package.json`은 바뀌었지만 실제 파일(`node_modules`)은 각자 설치해야 함
  - `npm install qrcode.react` 대신 `npm install`로 **목록에 있는 버전 그대로** 설치
- **회원가입 후 이동 위치가 매번 다른 문제** : 예매 화면을 볼 때마다 주소를 저장(`rememberBooking`)했다가 로그인·회원가입 후 그 주소로 보내는 구조라, 마지막으로 구경한 영화 화면으로 이동함 → 담당 팀원 코드를 확인하며 수정 방향 논의 중

#### 8. Troubleshooting

- `Error Code: 1451` (Cannot delete a parent row) → 좌석·예매 데이터가 시간표를 가리키고 있음 → 가리키는 쪽부터 순서대로 삭제
- `Error Code: 1175` (safe update mode) → Workbench가 기본 키 조건 없는 대량 삭제를 막음 → `SET SQL_SAFE_UPDATES = 0` 후 작업하고 끝나면 다시 `1`로 복구
- `Error Code: 2013` (Lost connection) → Workbench 기본 연결 시간 30초 초과 → **SQL Editor 설정**에서 read timeout을 늘리고 연결을 다시 열기
- 임시 테이블이 사라져 `Table 'tmp_g' doesn't exist` → 임시 테이블은 **연결이 유지되는 동안만** 존재해서, 재연결 후 사라짐 → 임시 테이블 없이 JOIN 삭제로 변경
- `Error Code: 1205` (Lock wait timeout) → Workbench 연결이 끊겨도 **MySQL 서버는 이전 삭제를 계속 진행**하며 테이블을 잠그고 있었음 → 끝날 때까지 기다린 뒤 확인하니 좌석이 이미 모두 삭제되어 있었음
- 실행 중 다른 탭에서 SQL이 안 됨 → 같은 연결의 탭은 함께 잠김 → **홈에서 연결을 하나 더** 열어서 진행 상황 확인
- `http proxy error ... ECONNREFUSED` → 화면 서버가 백엔드(8080)에 연결하지 못함 → 데이터 작업 중 **백엔드를 꺼둔 상태**라 정상, 백엔드 실행 후 해결

#### 9. 핵심 정리

- 순위별 최대 회차를 정하고 **가장 빨리 비는 관에 차례로 배치**하는 방식으로 인기 영화가 여러 관을 쓰는 시간표를 만듦
- 시간표를 정하는 값을 **설정값과 카카오 ID처럼 모두에게 같은 값**으로만 구성해 팀원 모두 같은 결과가 나오게 함
- 대량 데이터 삭제는 **외래 키 순서**를 먼저 파악하고, **나눠서 삭제**해야 연결 끊김과 잠금 문제를 피할 수 있음
- 팀원이 만든 공용 컴포넌트와 서비스는 **수정하지 않고 재사용**하고, 화면별 스타일은 그 화면 CSS에서만 조정함
- 레이아웃처럼 여러 방법이 가능한 작업은 **코드 수정 전에 후보를 비교하고 먼저 결정**하는 것이 효율적임
