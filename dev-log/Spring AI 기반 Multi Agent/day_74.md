# 74일차

## 데이터베이스 모델링 (Database Design): 엔터티·속성·관계, 슈퍼타입/서브타입, 정규화와 ERD 실습

#### 1. 데이터베이스 모델링 과정

<p align="center">
  <img src="../../training/Database%20Design/2026.10.26/day_74_1.png" alt="day_74" width="700">
</p>

| 단계 | 하는 일 | 산출물 |
| --- | --- | --- |
| 요구사항 분석 | 업무를 이해하고 요구사항을 수집 (인터뷰, 업무 문서 검토, 설문조사) | 요구사항 명세서, 업무 흐름도(DFD), 용어 사전 |
| 개념적 모델링 | 핵심 엔터티와 관계를 정의 | 개념 ERD, 엔터티 목록, 관계 정의서 |
| 논리적 모델링 | 속성, 키(PK·FK·UK), 정규화를 수행 | 논리 ERD, 테이블 정의서, 정규화 보고서 |
| 물리적 모델링 | 실제 DBMS에 맞게 데이터 타입, 인덱스, 파티션, 테이블스페이스 설계 | 물리 ERD, DDL 스크립트 |

데이터베이스 설계(Database Design)는 요구사항 분석 → 개념적 → 논리적 → 물리적 모델링 순서로 진행한다.

개념적 모델링은 "무엇을 관리할지(엔터티와 관계)", 논리적 모델링은 "어떤 구조로 관리할지(속성, 키, 정규화)", 물리적 모델링은 "실제 DB에 어떻게 만들지(타입, 인덱스)"를 정하는 단계이다.

설계가 끝나면 업무 요구를 정확히 이해했는지, 엔터티와 관계가 빠짐없이 정의되었는지, 정규화가 적절한지, 성능과 용량을 고려했는지 확인한다.

#### 2. 엔터티와 속성

| 용어 | 설명 | 예 |
| --- | --- | --- |
| 엔터티 (Entity) | 업무에서 관리해야 할 대상 | 고객, 계좌, 거래내역 |
| 속성 (Attribute) | 엔터티가 가지는 세부 정보 | 고객명, 연락처, 잔액 |
| 식별자 (PK) | 엔터티의 각 행을 유일하게 구분하는 속성 | 고객번호, 계좌번호 |
| 외래키 (FK) | 다른 엔터티의 PK를 참조하는 속성 | 계좌의 고객번호 |
| 유니크키 (UK) | PK는 아니지만 중복되면 안 되는 속성 | 사업자등록번호 |

엔터티는 업무 시나리오의 명사에서, 속성은 그 명사를 설명하는 정보에서 찾는다.

하나의 속성에는 하나의 값만 저장하고, 다른 속성으로 계산할 수 있는 값(파생 속성)은 꼭 필요할 때만 둔다.

#### 3. 관계와 식별·비식별 관계

| 구분 | 의미 | ERD 표기 |
| --- | --- | --- |
| 카디널리티 | 상대 엔터티와 몇 개씩 연결되는지 (1:1, 1:N, N:M) | 막대(1), 까마귀발(N) |
| 옵셔널리티 | 반드시 연결되어야 하는지, 없어도 되는지 | 막대(필수), 원(선택) |
| 식별 관계 | 부모의 PK가 자식의 **PK 일부**가 됨 | 실선 |
| 비식별 관계 | 부모의 PK가 자식의 **일반 컬럼(FK)**이 됨 | 점선 |

부모 없이는 의미가 없는 종속 엔터티(이력, 상세 항목 등)는 부모 PK를 자식 PK에 포함시키는 식별 관계로 설계한다.

자신만의 번호로 유일하게 구분되는 독립 엔터티는 부모를 FK로만 참조하는 비식별 관계로 설계한다.

N:M 관계는 중간 엔터티를 만들어 1:N 관계 두 개로 풀어낸다.

#### 4. 슈퍼타입과 서브타입

<p align="center">
  <img src="../../training/Database%20Design/2026.10.26/day_74_3.png" alt="day_74" width="650">
</p>

| 용어 | 설명 | 예 |
| --- | --- | --- |
| 슈퍼타입 (Supertype) | 공통 속성을 가진 상위 엔터티 | 직원: 사번, 이름, 입사일 |
| 서브타입 (Subtype) | 슈퍼타입을 상속받아 고유 속성을 추가로 가진 하위 엔터티 | 정규직: 퇴직금 기여율, 계약직: 계약 종료일 |
| 구분자 (Discriminator) | 어떤 서브타입인지 알려 주는 속성 | 직원구분코드 'R', 'C', 'P' |

<p align="center">
  <img src="../../training/Database%20Design/2026.10.26/day_74_2.png" alt="day_74" width="600">
</p>

| 관계 | 의미 | 구분자 방식 | 예 |
| --- | --- | --- | --- |
| 배타적 관계 (Exclusive) | 하나의 서브타입에만 속함 (× 기호) | 단일 코드 컬럼 1개 | 계좌 유형, 직원 고용형태 |
| 포함 관계 (Inclusive) | 여러 서브타입에 동시에 속할 수 있음 (열린 원 기호) | 플래그 컬럼 여러 개 | 판매 채널, 직원 겸직 역할 |

"A이면서 동시에 B일 수 있는가?"를 물어서 No이면 배타적 관계, Yes이면 포함 관계로 판단한다.

배타적 관계는 `account_type = 'D'`처럼 코드 컬럼 하나로, 포함 관계는 `online_yn = 'Y'`, `offline_yn = 'Y'`처럼 여부 컬럼 여러 개로 구분한다.

#### 5. 정규화

| 정규형 | 조건 | 해결 방법 |
| --- | --- | --- |
| 제1정규형 (1NF) | 모든 속성이 하나의 값(원자값)만 가짐 | 반복되는 값을 별도 행이나 엔터티로 분리 |
| 제2정규형 (2NF) | 복합 PK의 일부에만 종속되는 속성(부분 종속)이 없음 | 부분 종속 속성을 별도 엔터티로 분리 |
| 제3정규형 (3NF) | PK가 아닌 속성끼리 종속되는 경우(이행 종속)가 없음 | 이행 종속 속성을 별도 엔터티로 분리 |

정규화는 데이터 중복을 줄이고, 수정·삭제할 때 일부 데이터만 바뀌어 생기는 이상 현상을 막기 위해 엔터티를 분리하는 과정이다.

다만 너무 많이 나누면 조회할 때 조인이 많아져 느려질 수 있으므로, 조회가 많은 경우에는 일부 중복을 허용하는 반정규화도 함께 고려한다.

#### 6. 설문 시스템 모델링

| 엔터티 | 역할 |
| --- | --- |
| 설문지 | 설문 제목, 설명, 시작일·마감일, 상태 |
| 질문(설문문제) | 설문지에 포함된 문제, 문제유형(객관식·단답식·주관식), 필수여부 |
| 선택지(설문문항) | 객관식 문제의 보기 |
| 응답자(설문참여자) | 설문에 참여하는 사람 |
| 설문참여 | 설문지와 응답자의 N:M 관계를 풀어 주는 중간 엔터티 |
| 답변(설문결과) | 질문별 응답, 단답식·주관식은 응답내용에 저장 |
| 객관식선택결과 | 답변에서 고른 선택지, 여러 개 선택도 저장 가능 |

설문지 → 질문 → 선택지로 이어지는 설문 구성과, 응답자 → 설문참여 → 답변으로 이어지는 응답 흐름을 나누어 설계했다.

주관식과 단답식은 별도 엔터티로 나누지 않고 질문의 `문제유형`으로 구분하고, 객관식은 선택한 선택지 번호를, 단답식·주관식은 응답 내용을 저장한다.

#### 7. 은행 계좌관리 시스템 모델링 (Quiz)

| 엔터티 | 주요 속성 | 관계 |
| --- | --- | --- |
| 고객 | 고객번호(PK), 고객구분, 성명, 생년월일, 사업자등록번호, 연락처, 주소, 고객상태 | |
| 고객변경이력 | 고객번호(PK·FK), 변경순번, 변경항목, 변경전값, 변경후값, 변경일시 | 고객 1 : N (식별) |
| 금융상품 | 상품코드(PK), 상품명, 상품유형, 최소가입금액, 가입기간, 판매상태 | |
| 계좌 | 계좌번호(PK), 고객번호(FK), 상품코드(FK), 개설일자, 계약금리, 잔액, 지급정지금액, 계좌상태 | 고객·금융상품 1 : N (비식별) |
| 계좌상태이력 | 계좌번호(PK·FK), 상태시작일시(PK), 변경사유, 변경일시 | 계좌 1 : N (식별) |
| 거래내역 | 계좌번호(PK·FK), 거래순번, 거래일시, 거래유형, 거래금액, 거래후잔액, 이체번호(FK) | 계좌 1 : N |
| 이체 | 이체번호(PK), 출금계좌번호, 입금계좌번호, 이체금액, 처리상태, 실패사유 | 계좌 1 : N, 거래내역 1 : N |

고객정보, 계좌 개설, 입출금 거래, 계좌 상태 관리, 이체를 통합하는 은행 시나리오를 읽고 엔터티와 속성을 도출해 eXERD로 ERD를 작성했다.

금리가 바뀌어도 기존 계좌의 계약 조건을 확인할 수 있도록 개설 당시 금리를 계좌의 `계약금리`에 따로 저장하고, 해지된 계좌와 과거 거래내역은 삭제하지 않고 상태 값으로 관리한다.

동일한 요청이 중복으로 들어와도 한 번만 처리되도록 거래내역과 이체에 `요청고유번호`를 두고, 이체로 생긴 거래는 `이체번호`로 이체와 연결해 추적할 수 있게 했다.

#### 핵심 정리

- 데이터베이스 설계는 요구사항 분석 → 개념적 → 논리적 → 물리적 모델링 순서로 진행한다.
- 엔터티는 관리할 대상, 속성은 세부 정보, PK는 행을 유일하게 구분하는 식별자이다.
- 부모 PK가 자식 PK에 포함되면 식별 관계(실선), 일반 FK로만 쓰이면 비식별 관계(점선)이다.
- 부모에 종속되는 이력·상세 엔터티는 식별 관계, 스스로 유일한 독립 엔터티는 비식별 관계로 설계한다.
- N:M 관계는 중간 엔터티를 두어 1:N 관계 두 개로 풀어낸다.
- 슈퍼타입은 공통 속성, 서브타입은 고유 속성을 가지며 구분자로 서브타입을 판별한다.
- 하나에만 속하면 배타적 관계(코드 컬럼 1개), 여러 개에 동시에 속하면 포함 관계(여부 컬럼 여러 개)이다.
- 정규화는 중복과 이상 현상을 줄이기 위해 엔터티를 분리하는 과정이며, 성능을 위해 반정규화도 고려한다.

설문 시스템은 설문지, 질문, 선택지, 응답자, 설문참여, 답변, 객관식선택결과 7개 엔터티로 설계해 보았다.
</br>설문지와 응답자는 한 사람이 여러 설문에, 한 설문에 여러 사람이 참여할 수 있는 N:M 관계라서 설문참여라는 중간 엔터티를 두어 1:N 관계 두 개로 풀었다.
</br>또 객관식에서 여러 개를 선택하는 경우까지 저장하려면 답변 안에 선택지 번호 하나만 두는 것으로는 부족해서, 객관식선택결과를 따로 만들어 답변번호와 선택지번호를 함께 PK로 두어야 한다는 것을 알게 되었다.

<p align="center">
  <img src="../../training/Database%20Design/2026.10.26/day_74_6.png" alt="day_74" width="700">
</p>

처음에 만든 설문 시스템 ERD는 설문지 → 설문지 선택 → 설문지문항으로 이어지는 복합 키 구조에 설문참여자, 설문참여, 설문결과를 추가하는 방식으로 완성했다.
</br>설문결과는 참여번호, 문제번호, 참여자번호, 설문지번호를 모두 PK로 가지면서 키가 계속 늘어났고, 같은 설문지번호가 설문참여와 설문문제 양쪽에서 들어와 PK와 FK 관계가 복잡해졌다.
</br>같은 설문 시스템이라도 부모 키를 계속 물려받는 식별 관계 중심으로 설계할지, 엔터티마다 고유 번호를 두는 비식별 관계 중심으로 설계할지에 따라 구조가 크게 달라진다는 것을 두 ERD를 비교하며 느꼈다.
</br>ERD는 한 번에 정답을 그리는 것이 아니라 요구사항과 PK·FK를 계속 대조하며 고쳐 나가는 과정이라는 것을 오늘 실습을 통해 알게 되었고, 관계선 하나를 그릴 때도 왜 식별 관계인지, 왜 선택 관계인지 설명할 수 있어야 한다는 것을 느꼈다.

<p align="center">
  <img src="../../training/Database%20Design/2026.10.26/day_74_4.png" alt="day_74" width="700">
</p>

은행 고객·계좌·입출금 거래 시나리오를 읽고 eXERD로 고객, 고객 변경 이력, 금융상품, 계좌, 계좌상태이력, 거래내역, 이체 테이블을 만들어 ERD를 완성했다.
</br>처음에는 엔터티를 너무 잘게 나눠 13개까지 늘어났는데, 시나리오의 요구사항을 하나씩 대조해 보니 개인·기업고객은 고객구분으로, 상품금리 이력은 계좌의 계약금리로, 해지 정보는 계좌상태이력으로 충분히 관리할 수 있어서 7개로 줄일 수 있었다.
</br>관계선을 그리면서 식별 관계와 비식별 관계의 차이를 직접 확인할 수 있었다. 고객 변경 이력과 계좌상태이력처럼 부모의 PK가 자식의 PK에 들어가는 관계는 실선으로, 고객과 계좌처럼 부모의 PK가 일반 FK로만 들어가는 관계는 점선으로 표시되었다.
</br>다시 보니 고객 변경 이력의 `변경순번`, 거래내역의 `거래순번`도 PK에 포함되어야 행을 유일하게 구분할 수 있는데 빠져 있었고, 이체에는 정리하지 못한 `새 컬럼`이 남아 있어서 ERD를 완성한 뒤에도 PK 구성과 컬럼을 다시 점검해야 한다는 것을 느꼈다.
