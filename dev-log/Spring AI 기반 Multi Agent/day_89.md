# 89일차

## 최종 프로젝트 SpaceLink의 서비스 기획·요구사항 정의·화면 설계 정리

📌 학습일 : 2026.11.12

#### 1. 프로젝트 주제와 서비스 범위

- 서울의 청약 공고와 집·상가·오피스 정보를 모아 사용자의 조건에 맞는 후보를 추천하는 **SpaceLink** 서비스를 기획
- 청약 공고에는 예상 자격과 가점, 일정, 주변 환경, 준비 서류를 제공하고, 집·상가·오피스에는 가격·입지·건물 정보와 추천 근거를 제공하도록 범위를 구체화
- 온비드 서울 공매 물건은 별도 화면을 추가하지 않고 집·상가·오피스 목록에 함께 표시하며, 공매 라벨과 입찰 정보를 통해 일반 매물과 구분
- 서비스가 실제 청약 신청이나 공매 입찰을 대행하지 않고, 매물을 중개하거나 계약을 진행하지 않는다는 경계를 명시
- 오피스 공고는 해당 공급기관의 공식 공고·신청 페이지를 확인할 수 있도록 연결하는 방향으로 정리

#### 2. 역할 분담과 개발 일정

| 담당 | 주요 역할 |
| --- | --- |
| 이연화(팀장) | 구조 설계, 데이터 수집, 청약 자격·가점, 추천·지도, 집·상가·오피스 분석, 메인 AI 검색·추천과 개인화 알림, 후보 비교·AI 추천 이유, 공고 조건 추출, 배포 및 담당 페이지 테스트 |
| 정려립 | 로그인·회원가입·계정 찾기, 청약·희망 조건 입력, 매물 찜과 마이페이지 연동, 관리자·고객센터·AI 상담, 이메일, 공통 화면 프론트엔드 구현 및 담당 페이지 테스트 |

- 2인 담당 기능을 화면과 연결하고, 찜 데이터가 매물 상세에서 등록·해제된 뒤 마이페이지와 후보 비교에 전달되는 의존 관계를 확인
- 11월 16일부터 12월 11일까지 주차별 구현을 진행하고 12월 12일에 최종 발표하는 일정으로 1차·2차·3차 기능을 구분
- 데이터 적재와 목록·상세 구현을 먼저 진행하고, 상세 화면에서 찜할 수 있는 시점에 맞춰 마이페이지 연동을 확인하도록 순서를 구성

#### 3. 요구사항 정의서 작성

Excel 요구사항 정의서에 기능을 담당자와 화면까지 추적할 수 있도록 정리하였다.

- 총 **60개 요구사항**에 ID, 구분, 기능명, 상세 내용, 완료·검증 기준, 관련 화면 ID, 우선순위, 정의 상태, 담당자, 비고·제약을 기록
- P1 36개, P2 22개, P3 2개로 나누어 1차 발표에 필요한 기능과 후속 기능을 구별
- 회원 인증, 청약 프로필, 추천, 지도, 공매, 알림, 관리자, 데이터 수집 등 기능별로 요구사항을 분류
- 47개는 정의 완료, 8개는 초안·검토, 5개는 미정·검증 필요로 상태를 구분
- 별도 화면 목록에 33개 화면 ID를 정리하고, 미결사항 시트에는 화면 추적성, 외부 API, 점수 기준, 데이터 검증과 범위 결정 등 15개 항목을 기록

요구사항마다 완료·검증 기준을 함께 적어 기능이 구현되었는지를 확인할 수 있게 했다. 예를 들어 로그인 요구사항에는 잠금 조건과 오류 처리 기준을, 데이터 입력에는 저장 후 재조회와 미입력 상태의 표시 기준을 연결했다.

#### 4. 화면 설계와 사용자 흐름

- 화면설계서는 총 36장으로 구성하고, 메인 홈·회원·청약·공간·고객센터·마이페이지·관리자 영역의 33개 화면 ID를 상세 명세와 연결
- 메인 홈에 AI 검색·추천, 조회수 기준 매물 Top 5, 추천 카드, 청약 일정 캘린더, 공지와 바로가기를 배치
- 회원 흐름은 가입·로그인 뒤 청약 프로필과 찾는 대상·희망 조건을 입력하도록 정리
- 찾는 대상 화면에서는 **공통 희망 지역을 먼저 설정**하고, 집·상가·오피스별로 다른 지역을 원할 때만 “다르게 지정하기”를 선택하도록 정의
- 목록·상세, 지도, 찜, 마이페이지, 후보 비교가 연결되도록 화면 전환과 API·상태 변경 지점을 기록
- 청약 공고 조건 검토, 관리자 승인, 고객 문의, 알림 발송 등 운영 화면도 사용자 화면과 함께 명세

화면별 설명에는 화면 ID뿐 아니라 주요 기능, 이동 경로, 관련 API와 Check Point를 적어 화면 설계와 요구사항을 서로 확인할 수 있게 했다.

#### 5. 입력 정보와 데이터 구조

- 회원가입 정보와 청약 프로필을 분리하고, 내·외국인 정보는 가입 화면이 아니라 맞춤 청약 조건의 기본·거주 항목에서 입력하는 흐름으로 정리
- 청약 정보는 기본·거주, 혼인·가족·세대, 주택, 청약통장, 당첨 이력, 소득·자산, 희망 조건의 7개 섹션으로 구분
- 테이블 초안은 `MEMBER`, `SUBSCRIPTION_PROFILE`, `SUBSCRIPTION_HOUSEHOLD`, `SUBSCRIPTION_CAR`, `SEARCH_PREFERENCE`로 구성
- 세대원과 보유 차량을 청약 프로필의 단일 값에 묶지 않고 별도 테이블로 관리하도록 구분
- 공통 희망 지역과 대상별 지역 설정을 함께 저장할 수 있도록 검색 선호 구조를 고려
- 주민등록번호, 외국인등록번호, 청약통장 번호, 증빙서류는 수집하지 않고 금액은 구간으로 받으며 민감 정보는 암호화 저장
- 입력이 없거나 값이 “모름”인 경우 자격을 확정하지 않고 “확인 필요”로 안내하며, AI에 식별 정보·소득·자산·가족 정보를 보내지 않는 원칙을 명시

#### 6. 기술 구성과 데이터 출처 정리

- Web, Data, AI 역할을 나누고 Spring Boot, Spring Security, MyBatis, Oracle, Redis, Spring AI, Spring Batch 등 적용 위치를 기획서에 정리
- AI는 자연어 조건 변환, 추천 사유, 공고 조건 초안과 고객상담 등에 활용하고, 자격·가점 계산은 규칙과 점수 로직으로 분리
- 청약홈·LH·마이홈·국토교통부 실거래·건축HUB·온비드·네이버 지도 등 기능별 데이터 출처와 연결 범위를 정리
- API 필드와 호출 한도는 신청 후 검증이 필요하므로, 계획된 데이터와 실제 확인된 데이터를 구분
- 데이터 적재, 조회, 오류 재시작, 좌표·주소 연결, 정보 출처와 기준일 표시를 설계 고려사항에 포함

#### 7. 검토할 사항과 Troubleshooting

- 요구사항·화면·담당자·우선순위를 함께 관리하지 않으면 같은 기능이 문서마다 다른 이름이나 범위로 남을 수 있어 화면 ID를 공통 연결 기준으로 사용
- 외부 자료의 수정 내용을 합칠 때 기존 확정 사항인 공통 희망 지역 우선 흐름과 세대원·차량 테이블을 보존하면서 최신 화면의 메인 홈 변경을 반영
- 기획안 개요에는 개발 기간이 `11/18~12/18`로 적혀 있지만, 주차별 일정에는 `11/16~12/12`로 기록되어 있어 최종 문서에서 날짜를 통일할 필요가 있음
- 청약·공매 데이터의 실제 API 필드, 자격 규칙과 가중치, 화면 ID와 최종 PDF의 대응, 1차 기능 범위 등 15개 미결사항을 다음 검토 대상으로 정리

#### 핵심 정리

- SpaceLink의 서비스 범위와 하지 않는 역할을 구분하고, 집·상가·오피스·청약 공고의 주요 기능을 정리함
- 60개 요구사항에 검증 기준과 화면 ID를 연결해 기능의 담당·우선순위·진행 상태를 추적할 수 있게 함
- 공통 희망 지역과 대상별 예외 지역, 찜에서 마이페이지·후보 비교로 이어지는 사용자 흐름을 구체화함
- 세대원과 차량 데이터를 분리하고 민감 정보 처리 원칙을 설계에 반영함
- 남은 검증 항목과 개발 일정의 불일치를 확인해 개발 전에 정리해야 할 결정을 드러냄

---

오늘은 SpaceLink 프로젝트의 서비스 기획서, 요구사항 정의서, 화면설계서를 함께 정리했다. 기능을 나열하는 데서 멈추지 않고 요구사항 ID와 화면 ID, 담당자, 우선순위, 완료 기준을 연결해 각 기능을 어떻게 구현하고 확인할지 문서로 맞춰 보았다.
</br>특히 찾는 대상 화면에서 공통 지역을 먼저 받고 필요한 경우에만 대상별로 지역을 바꾸는 흐름, 매물 상세에서 등록한 찜이 마이페이지와 후보 비교로 이어지는 흐름처럼 화면 사이의 데이터 의존성을 함께 확인했다.

기획서와 화면설계서, 요구사항 정의서가 서로 맞아야 실제 개발 때 담당 범위와 완료 기준을 같은 의미로 이해할 수 있다는 점을 배웠다. 아직 외부 API 필드와 추천 기준, 화면 ID 대조처럼 확인이 필요한 내용이 남아 있으므로, 확정 사항과 검증 전 가정을 구분해 관리해야겠다고 느꼈다.

다음에는 미결사항 중 우선순위가 높은 데이터 API와 화면 범위를 확인하고, 일정과 기획 개요의 개발 기간을 통일한 뒤 각 P1 요구사항을 구현 작업으로 나누어 볼 계획이다.
