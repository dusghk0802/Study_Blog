# 91일차

## SpaceLink 공고·매물 데이터 저장 방식과 ERD 재검토

📌 학습일 : 2026.11.14

📌 학습 내용 : Final Project, ERD Revision, Real-time API, Oracle DB, Redis Cache, Data Pipeline, Public Notice, Data Retention, Recommendation Alert

---

#### 1. 어제 학습일지와 비교해 달라진 점

- 어제는 전체 55개 테이블을 기준으로 건물·공매 상세를 외부 API에서 실시간으로 가져와 Redis에 캐시하는 방향을 정리했다.
- 오늘은 최신 기획안과 ERD 목록을 다시 대조해 테이블 수를 **50개**로 정리하고, 어떤 데이터를 DB에 남기며 어떤 데이터는 상세 조회 때 API에서 가져올지 구분했다.
- 어제는 일반 집·상가·오피스 매물도 외부 신청 페이지로 연결하는 것으로 정리했지만, 오늘 기획안에서는 일반 건물은 매물이 아니라 분석 대상이라고 명확히 했다. 일반 건물에는 신청 버튼을 두지 않고, 공공 공고는 공급기관 공식 신청 페이지로, 공매 물건은 온비드 입찰 페이지로 연결한다.
- 오늘은 공고 데이터 전체를 저장할지 실시간으로만 조회할지 다시 검토했다. 결론은 공고 데이터를 전부 저장하거나 전혀 저장하지 않는 두 방식 중 하나를 택하는 것이 아니라, 기능에 필요한 최소 정보는 DB에 저장하고 상세 정보는 실시간 API와 Redis 캐시를 사용하는 혼합 방식이다.

#### 2. 공고·건물·공매 데이터의 저장 범위 구분

| 데이터 | DB에 저장하는 내용 | 상세 조회 때 가져오는 내용 |
| --- | --- | --- |
| 청약·공공 공고 | 목록·지도·필터·판단에 필요한 최소 정보, 일정, 승인된 조건 | 사업 주체·시공사·공급 세대수·신청 링크 등 상세 정보는 원천 API에서 조회하고 Redis에 캐시 |
| 공공 상가·오피스 공고 | 공고와 관리자 확인을 마친 공급 호실·조건 | 상세 공고 정보와 신청 링크는 공급기관 API에서 조회 |
| 건물 | 목록·지도·점수 계산에 필요한 기본 정보 | 구조·층수·연면적·사용승인일·엘리베이터·용도지역·정화조 용량 등은 건축HUB·토지 API에서 조회하고 Redis에 캐시 |
| 공매 물건 | 목록·지도에 필요한 정보 | 용도 세부·소재지·유찰·지분·온비드 링크·회차별 입찰 정보는 온비드 API에서 조회하고 Redis에 캐시 |

- 원천 API의 전체 응답을 그대로 Oracle에 복사하는 것이 아니라, 목록·지도·검색·상태 확인처럼 여러 기능에서 공통으로 쓰는 값만 저장한다.
- 상세 화면에서 최신성이 중요한 값은 필요할 때 API로 조회한다. Redis는 반복 호출을 줄이기 위한 캐시이므로 원본 DB와 같은 영구 저장소로 취급하지 않는다.
- 공고문과 첨부파일, AI가 추출한 조건, 관리자가 승인한 최종 조건처럼 자격 판단과 검토에 필요한 데이터는 별도로 저장한다.
- 공고와 공매 데이터는 종료 후 30일이 지나면 관련 문서·벡터·찜·비교·알림·판정 결과와 함께 삭제하도록 보관 기준을 정리했다.

#### 3. 새 공고 알림은 조회 요청이 아닌 수집 이벤트로 처리

- 사용자가 공고 목록을 열 때마다 새 공고를 찾아 모든 회원에게 알림을 보내는 구조는 아니다.
- Data 서버가 API를 주기적으로 확인해 새 공고를 수집하면, 서버가 저장된 최소 공고 정보와 회원의 희망 조건을 규칙으로 매칭한다.
- 매칭된 회원에게 알림 이벤트를 만들고 이메일을 발송한다. 중복 발송 방지와 재시도를 위해 공고 식별자와 알림·발송 상태는 기록해야 한다.
- AI는 모든 회원을 대상으로 조건을 판정하는 데 쓰기보다, 서버가 추린 결과의 추천 이유를 작성하는 등 필요한 작업에 제한한다. 소득·자산·가족 정보는 OpenAI에 보내지 않는다.
- API가 바뀌거나 일시적으로 중단될 수 있으므로 수집 주기, 호출 한도, 마지막 정상 확인 시각, 재시도와 오류 기록도 함께 고려해야 한다.

#### 4. 기획·ERD에서 다시 확인한 데이터 설계

- 최신 ERD 산출물의 테이블 수는 **50개**로 일치한다. 청약 프로필은 한 회원의 선택값을 한 행에 저장하고, 가구원 수·자동차 대수와 차량 가액 구간도 간단한 선택값으로 표현한다.
- 청약 통장은 본인·배우자 보유 여부와 신청자 통장 정보, 둘 다 보유한 경우 배우자 가입 기간을 구분하도록 정리했다.
- 청약 프로필의 금액·기간 구간 경계는 공통코드로 관리하고, 실제 공고 기준과 걸리는 값은 확정 판정 대신 ‘확인 필요’로 안내한다.
- 기획안과 ERD의 조건 저장 방식, API가 실제로 제공하는 필드·식별자, 일정 중복 가능성은 구현 전에 계속 대조해야 할 항목으로 남겼다.

#### 5. 핵심 정리

- “API 실시간 조회”와 “DB 저장”은 서로 배타적인 선택이 아니다. 반복해서 쓰는 최소 데이터는 Oracle에 저장하고, 최신 상세는 API에서 가져와 Redis에 캐시할 수 있다.
- 공고 알림을 보내려면 사용자가 조회하지 않는 동안에도 API를 확인하는 수집 작업과 신규 공고를 식별할 기준이 필요하다.
- 일반 건물 분석, 공공 공고, 공매는 서비스에서 제공하는 기능과 외부 연결 경로가 서로 다르므로 데이터 유형을 구분해야 한다.
- 테이블 수를 줄이는 것만으로 ERD가 단순해지는 것은 아니다. 어떤 화면·알림·판정 기능이 데이터를 필요로 하는지 먼저 정하고 저장 범위를 결정해야 한다.

---

오늘 ERD를 검토하면서 가장 크게 배운 점은 **‘실시간 API를 쓴다’는 말만으로 DB 저장 여부를 결정할 수 없다는 것**이다. 처음에는 공고를 DB에 저장하면 실시간이 아니게 된다고 생각했지만, 실제로는 API를 주기적으로 확인해 DB의 최소 공고 정보를 갱신하고, 사용자의 상세 조회 때 최신 세부 정보를 API에서 불러오는 방식으로 함께 운영할 수 있다. 새 공고 이메일 알림도 사용자가 페이지를 방문할 때 처리하는 것이 아니라, 수집 이벤트를 감지하고 조건을 매칭하는 별도 흐름이 있어야 한다.
</br>또 하나의 혼선은 기획안에 이미 정리된 데이터 정책을 확인하지 않고, 공고 저장 여부가 아직 결정되지 않은 것처럼 답했던 점이다. 기획안에는 공고 수집·저장, 승인, 알림, 종료 후 삭제가 적혀 있었고, 상세 일부만 API 실시간 조회와 캐시로 처리하도록 되어 있었다. ERD를 검토할 때는 테이블 이름이나 기술 선택만 보는 것이 아니라 기획서의 데이터 흐름과 보관 정책까지 함께 읽어야 한다고 느꼈다.

어제는 데이터 모델의 크기와 구성을 중심으로 살펴봤다면, 오늘은 데이터가 언제 수집되고, 어떤 기능에 쓰이며, 언제 삭제되는지까지 연결해 생각했다. 앞으로는 API 응답 원본, 서비스 DB의 핵심 데이터, Redis 캐시를 분리해 설명하고, 각 데이터가 필요한 기능과 수명 주기를 근거로 ERD를 검토해야겠다.
