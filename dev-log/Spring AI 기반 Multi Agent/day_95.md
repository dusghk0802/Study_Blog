#### 1. SpaceLink의 기획 기준과 화면 구성을 문서에 맞췄다

오늘은 SpaceLink를 서울의 청약·공공 공고와 집·상가·오피스 정보를 함께 탐색하고 추천받는 서비스로 정리했다. 청약 신청이나 공매 입찰을 대신하지 않고, 공식 신청 페이지로 연결한다는 서비스 범위도 문서에 명확히 적었다.

화면 구성에는 집·상가·오피스 매물과 모집 중인 청약·공공 공고를 한 지도에서 보는 **매물 지도(UI-010)**를 독립된 상단 메뉴로 반영했다. 핀 유형 필터와 지도 범위 검색, 마커 클러스터, 핀에서 상세 화면으로 이동하는 흐름도 요구사항과 스토리보드에 연결했다.

요구사항 정의서, 테이블 정의서, 핵심 기능 시퀀스 흐름 정의서, UI 스토리보드, WBS는 각각 기능 기준, DB 필드, 호출 순서, 화면 구성, 담당과 일정을 기록한다. 같은 기능이 문서마다 다른 표현으로 남으면 개발 중 해석이 달라질 수 있으므로 ID와 담당 범위를 맞추는 일이 중요하다는 점을 배웠다.

| 산출물 | 정리한 기준 |
| --- | --- |
| 기획서·요구사항 정의서 | 서비스 범위, 기능과 완료 기준, 화면 ID, 우선순위, 담당자 |
| 테이블 정의서 | 테이블·컬럼의 물리명과 논리명, 자료형, 키와 제약 |
| 시퀀스 흐름 정의서 | 사용자·웹·외부 인증기관·DB·분리 서버 사이의 요청 순서 |
| UI 스토리보드 | 화면별 주요 컴포넌트, 동작, 연결 요구사항과 이동 화면 |
| WBS | 준비부터 최종 발표까지 주차별 업무, 담당자, 완료 목표 |

#### 2. 3대 EC2와 서비스별 접근 경계를 아키텍처에 표현했다

아키텍처 그림은 기술 로고만 나열하는 자료가 아니라, 브라우저 요청이 어떤 서버와 서비스를 거쳐 처리되는지를 보여 주는 자료로 정리했다. EC2를 Web, DB, Data·AI 세 대로 구분하고 각 서버의 역할과 외부 공개 범위를 함께 표시했다.

| 서버 | 주요 역할 | 접근 원칙 |
| --- | --- | --- |
| Web EC2 | Nginx, React 정적 파일, Spring Boot 웹 기능, 인증·메일 | 외부 HTTPS 요청을 받음 |
| DB EC2 | Oracle AI Database, Spatial, 벡터 검색, PL/SQL 점수·추천 패키지 | 애플리케이션 서버에서만 접근 |
| Data·AI EC2 | Spring Batch 수집, 공고문 처리, AI 검색·추천·상담 | 외부 직접 접속을 막고 Web·DB와 필요한 경로만 연결 |

문서에 적힌 주요 버전은 Java 21, Spring Boot 3.5.16, Spring AI 1.1.8, React 19.3.1, Vite 8.3.8, Node.js 24 LTS, Nginx 1.30, Redis 8.10, Oracle AI Database 26ai Free 등이다. Oracle 계정도 Web·Data·AI 용도별로 나누고, Data 앱은 회원 정보에 접근하지 않으며 AI 앱은 문서 벡터 데이터만 접근하도록 경계를 설정했다.

배포 흐름에는 GitHub → GitHub Actions → GHCR → Docker Compose → EC2를 표시했다. 이를 통해 코드 저장·검증·이미지 배포가 운영 서버 실행까지 어떻게 이어지는지 한눈에 볼 수 있게 했다.

#### 3. API 키, 서비스 URL, Base URL, 기능 경로를 구분했다

API 명세서는 API ID, 신청·발급 페이지, 진행 상태, End Point/Base URL, 기능별 호출 경로, HTTP 방식, 데이터 형식, 인증 방식, `.env` 변수명, 호출 제한, 타임아웃, 요청 파라미터·응답 필드·테스트 기록을 적을 수 있도록 정리했다. 공공데이터포털의 일반 인증키는 여러 API에서 공통으로 쓸 수 있지만, 각 데이터 서비스의 활용 신청과 승인은 별도로 확인해야 한다.

오늘 대화에서는 VWorld 개발키, API 호출 주소, VWorld에 등록하는 서비스 URL이 서로 다른 값이라는 점을 확인했다. VWorld 서비스 URL은 키를 사용할 웹사이트 도메인으로, 로컬 개발에서는 `http://localhost:5173/`을 등록할 수 있다. `5173`은 Vite의 기본 개발 포트이며, 프로젝트 설정이나 포트 충돌에 따라 달라질 수 있으므로 실제 실행 주소도 확인해야 한다.

GIS 건물 통합정보처럼 특정 데이터 API를 호출할 때는 해당 API의 명세에서 정확한 기능 경로와 필요한 인증 방식을 확인한다. 키 발급 화면에 End Point가 없더라도 호출 주소가 없는 것은 아니다. API 명세에서 키와 주소를 따로 관리하고, 실제 인증키 값은 `.env`에만 두며 저장소에는 올리지 않는 원칙도 정리했다.

| 항목 | 의미 | 예시 |
| --- | --- | --- |
| 서비스 URL | API 제공자에 등록하는 내 서비스 도메인 | `http://localhost:5173/` |
| Base URL / End Point | API 서버의 기본 호출 주소 | API 문서에서 확인 |
| 기능 호출 경로 | 특정 데이터·기능을 요청하는 경로 | GIS 건물 통합 WFS 경로 등 |
| 환경변수 이름 | 코드에서 인증키를 읽는 키 이름 | `VWORLD_API_KEY` |
| 인증키 값 | 실제 발급된 비밀값 | `.env`에 보관하고 Git에는 제외 |

#### 4. GitHub Desktop의 실제 diff로 커밋 범위를 확인했다

커밋 메시지는 대화에서 추측해 정하는 것이 아니라 GitHub Desktop의 변경 파일 목록과 diff에 맞춰야 한다는 점을 확인했다. 현재 화면에는 `.env.example` 삭제와 `.gitignore` 수정이 표시되고, 실제 `.env`는 변경 목록에 나타나지 않았다. diff에서는 `.gitignore`의 `.env.example` 예외 규칙이 제거된 것을 확인했다.

따라서 변경이 의도된 경우의 커밋 메시지는 다음과 같이 정리할 수 있다.

```text
chore: 환경변수 예시 파일 제거 및 ignore 규칙 정리
```

이 제목은 예시 파일 삭제와 ignore 규칙 변경을 모두 설명한다. 커밋 전에 변경 파일과 diff를 확인해야 제목이 실제 변경 내용과 일치하며, `.env`와 API 키 같은 비밀정보가 커밋에 포함되지 않았는지도 함께 확인할 수 있다.

#### 핵심 정리

- 서비스 범위와 화면·요구사항 ID를 여러 산출물에서 일치시켜야 구현 기준이 흔들리지 않는다.
- 매물 지도는 청약 공고와 집·상가·오피스 정보를 함께 보여 주는 독립 메뉴로 정의했다.
- 아키텍처는 3대 EC2의 역할, 공개 경계, DB 계정별 접근 범위, 배포 경로까지 나타내야 한다.
- API 키, 서비스 URL, Base URL, 기능 호출 경로는 서로 다른 값이므로 각각의 용도에 맞게 기록해야 한다.
- Vite의 `5173`은 기본 포트이며, 실행 설정이나 포트 충돌 여부에 따라 실제 주소를 확인해야 한다.
- 커밋 메시지는 GitHub Desktop에서 확인한 변경 목록과 diff를 요약해야 한다.
- `.env`와 API 키는 Git에 올리지 않고, 커밋 전 diff에서 민감정보 포함 여부를 확인한다.

---

오늘은 프로젝트 산출물이 각각 따로 존재하는 파일이 아니라 하나의 개발 기준을 서로 다른 관점에서 설명한다는 점을 배웠다. 기획서에서 정한 메뉴와 기능이 요구사항 ID, DB 구조, 시퀀스 흐름, 화면 스토리보드, WBS에 같은 의미로 반영되어야 개발자가 같은 기능을 만들 수 있다.

또 API 연동에서는 인증키만 발급받는다고 호출 준비가 끝나는 것이 아니었다. 키의 발급처와 등록 도메인, API 기본 주소, 기능별 호출 경로, 요청 파라미터를 각각 확인해야 했다. VWorld의 `http://localhost:5173/`은 개발 서비스 도메인이고, API End Point는 실제 데이터를 요청하는 서버 주소라는 차이를 정리했다.

아키텍처와 API 명세를 구체화하면서, 기술 이름만 적는 것보다 버전·역할·연결 방식·접근 범위를 함께 적어야 다른 사람이 보고 실제 구조를 이해할 수 있다는 것을 느꼈다. 특히 API 키 변수명을 명확히 나누고 `.env`를 저장소에서 제외하는 일은 보안뿐 아니라 팀원 간 설정 실수를 줄이는 데도 필요하다.

커밋 메시지도 변경 목록과 diff를 확인한 다음 작성해야 한다. 파일 이름만 보고 내용을 추측하면 삭제나 설정 변경을 놓칠 수 있다. 앞으로는 실제 변경 내용을 먼저 확인하고, 그 결과에 맞춰 커밋 제목과 설명을 작성해야겠다고 느꼈다.
