# 94일차

## SpaceLink 매물 추천 가중치와 ERD·문서 정합성 수정

📌 학습일 : 2026.11.18

📌 학습 내용 : 추천 점수 가중치 모델, 계산 결과 저장 여부, ERD와 기획서·요구사항·화면설계서 정합성

---

#### 1. 어제 학습일지와 비교해 달라진 점

- 93일차에는 서비스 흐름과 역할 분담, 요구사항, 화면설계서, WBS를 맞추는 작업에 집중했다. 94일차에는 매물 추천 점수 구조를 현재 ERD에 맞게 정리하고, 그 변경을 기획서·요구사항 정의서·화면설계서와 ERD 문서에 반영했다.
- 추천 가중치가 사용자 유형별인지 매물 용도별인지 다시 확인했다. 사용자 유형은 매물 기본 가중치를 정하지 않고, 집·상가·오피스 용도에 따라 각각 고정된 기본 가중치를 적용하기로 했다.
- 점수 결과를 Oracle에 계속 저장하는 구조와 요청할 때 계산하고 Redis에 캐시하는 구조의 차이를 검토했다. 항목별 매물 점수 테이블을 두지 않는 현재 설계로 문서 내용을 통일했다.

#### 2. 기본 가중치와 회원 선호 가중치 구분

- `SCORE_WEIGHT`에서 `USER_TYPE`을 제거하고 `SPACE_CATEGORY`, `FACTOR`, `WEIGHT`로 용도별 기본 가중치를 관리한다. 집·상가·오피스의 기본 가중치 합계는 각각 100점이다.
- 같은 평가 항목은 여러 용도에서 사용할 수 있으므로 `(SPACE_CATEGORY, FACTOR)` 두 컬럼의 조합에 복합 UNIQUE를 적용한다. 두 컬럼을 각각 UNIQUE로 설정하면 교통처럼 여러 용도에서 공통으로 쓰는 항목을 저장하지 못한다는 점도 확인했다.
- 회원이 저장한 선호는 `MEMBER_SCORE_WEIGHT`에 회원·용도·평가 항목별로 저장하고, 회원과 용도별 합계는 30점으로 관리한다. 이 테이블은 기본 가중치와 역할이 다르므로 집·상가·오피스 기본 점수와 구분해 적용한다.
- 기본 가중치는 용도마다 합계 100이 되도록 다음처럼 맞췄다.
  - 집: 교통 18, 인프라 16, 안전 13, 학군 6, 소음 14, 침수 11, 악취 6, 가격 16
  - 상가: 교통 10, 소음 5, 침수 10, 악취 10, 가격 15, 상권 20, 유동인구 15, 상가 업종 적합도 15
  - 오피스: 교통 25, 인프라 10, 안전 10, 소음 15, 침수 10, 악취 10, 가격 15, 오피스 업종 적합도 5
- 공통 코드와 컬럼 설명도 실제 항목에 맞춰 `STORE_FIT`, `OFFICE_FIT`을 반영했다. 회원이 저장하는 추가 선호에는 `HEATING_INSULATION` 항목을 포함하도록 구분했다.

#### 3. 계산 점수의 저장 위치와 갱신 방식 정리

- `PLACE_SCORE` 테이블을 두고 대상별 평가 점수를 Oracle에 저장하는 대신, 검색 요청 때 원천 데이터와 기본 가중치, 회원 선호, 현재 검색 조건을 이용해 점수를 계산한다.
- 계산된 평가점수와 최종 추천 점수는 Redis 캐시를 활용한다. 원천 데이터나 평가 기준, 가중치, 회원 선호 또는 검색 조건이 바뀌면 캐시를 갱신하고 다시 계산한다. 점수를 Oracle에 중복 저장하지 않아 원천 데이터 변경 뒤 오래된 점수가 남는 문제를 줄일 수 있다.
- 주변 환경 요약인 `PLACE_ENV`는 매물 평가 점수와 역할이 달라 유지한다. `PLACE_ENV`에는 침수·소음·악취 등 주변 환경 결과와 계산 시각을 저장하고, 추천 점수는 검색 시 계산한다.
- 청약 자격 판단·청약 가점과 매물 추천 점수도 별도 결과로 구분했다. 이름에 ‘점수’가 포함되어도 `SCORE_TABLE`의 청약 가점 규칙과 매물 추천 가중치·평가 결과는 목적이 다르다는 점을 확인했다.

#### 4. 관련 문서에 변경사항 동기화

- 기획서의 점수 갱신 설명에서 `PLACE_SCORE` 저장을 전제로 한 문구를 제거하고, 요청 시 계산·Redis 캐시·캐시 재계산 기준을 기재했다. 추천 점수 근거 화면에는 계산된 평가점수와 기본 가중치, 반영점수를 표시하도록 정리했다.
- 요구사항 정의서의 집·상가·오피스 추천 설명을 현재 확정 가중치로 바꾸고, 평가 항목별 점수와 가중치, 확인 필요 자료의 표시 기준을 맞췄다. 기본 가중치 합계가 100점이고 회원 선호 가중치는 별도 합계 30점이라는 점도 반영했다.
- 화면설계서 `USR_PREF-01`에서 사용자 유형이 대상별 기본 가중치를 정한다는 문구를 바꿨다. 사용자 유형은 AI 추천 이유에 사용하고, 매물 기본 가중치는 용도별 고정값을 사용하도록 했다.
- 테이블 목록과 DBML은 `PLACE_SCORE`를 제거하고, 분리된 집·상가·오피스 희망 조건 테이블과 현재 가중치 컬럼을 반영했다. 두 문서의 테이블 수와 이름을 기준 SQL과 대조해 모두 49개로 맞췄다.

#### 5. 오늘 작업에서 배운 점

- 데이터베이스에는 원천 정보와 지속적으로 관리해야 할 입력·규칙을 저장하고, 원천이 바뀌면 다시 계산할 수 있는 파생 결과는 캐시할 수 있다. 저장할 데이터와 계산할 데이터를 나누면 갱신 책임과 오래된 결과 문제를 더 명확히 다룰 수 있다.
- 복합 UNIQUE는 각 컬럼을 따로 유일하게 만드는 설정이 아니라, 두 값의 조합이 중복되지 않게 하는 제약이다. 집의 교통 가중치와 상가의 교통 가중치는 각각 저장할 수 있지만, 같은 용도 안에서 같은 평가 항목을 두 번 등록할 수 없게 한다.
- ERD를 바꾼 뒤에는 기획서의 계산 방식, 요구사항의 완료 기준, 화면의 설명, 공통 코드와 테이블 목록을 함께 대조해야 한다. 한 문서만 최신이어도 다른 문서가 이전 구조를 설명하면 개발자가 서로 다른 모델을 구현할 수 있다.

---

오늘 가장 크게 배운 점은 추천 점수를 저장할지 매번 계산할지를 단순한 테이블 개수 문제가 아니라 데이터의 성격과 갱신 방식으로 결정해야 한다는 것이다. 매물 항목 점수는 원천 정보와 가중치로 다시 계산할 수 있으므로 Oracle에 중복 저장하지 않고 검색 시 계산해 Redis 캐시를 쓰는 방향으로 정리했다. 반면 기본 가중치와 회원이 저장한 선호는 다음 요청에도 필요한 기준값이므로 데이터베이스에서 관리한다.

또한 ERD의 컬럼 하나를 바꾸는 일도 기획서의 알고리즘, 요구사항의 검증 기준, 화면에 보여 줄 문구까지 연결되어 있다는 걸 확인했다. 오늘 여러 문서를 대조하면서 기준 문서와 숫자를 먼저 확인하고, 변경 이유와 적용 범위를 함께 정리해야 나중에 구현과 테스트에서 혼선이 줄어든다고 느꼈다.
