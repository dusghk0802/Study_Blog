#### 1. 반정규화

| 구분 | 설명 |
| --- | --- |
| 정규화 | 중복을 줄이고 이상 현상을 막기 위해 테이블을 나누는 과정 |
| 반정규화 | 정규화 이후 **조회 성능**을 위해 일부 중복을 허용하고 조인 수(테이블 수)를 줄이는 과정 |

반정규화는 "조회 성능 → 조인 수를 줄인다 → 테이블 수를 줄인다"는 흐름으로, 반드시 정규화를 먼저 한 뒤에 적용한다.

중복을 허용하는 만큼 원본 값이 바뀌면 중복된 값도 함께 바꿔야 하는 무결성 문제가 생길 수 있으므로, 트리거 등으로 함께 관리할 방법까지 설계 단계에서 고려해야 한다.

#### 2. 컬럼 반정규화

| 방법 | 실습 예 | 내용 |
| --- | --- | --- |
| 중복 컬럼 추가 | 사원정보 + 업무지점 | 사원을 조회할 때 항상 지점명도 함께 조회 → 사원정보에 `지점명`을 중복으로 두어 조인 제거 |
| 파생 컬럼 추가 | 주문 + 주문제품 + 제품 | 조회의 90%가 총금액(수량 × 단가) 계산 → 주문에 `총금액` 컬럼 추가 |
| 이력 테이블 컬럼 추가 | 공사내역, 직원차량이력관리 | `공사비누적액`, `최근등록여부`처럼 이력에서 자주 찾는 값을 컬럼으로 추가 |
| PK 분리 | 차량 | 차량번호(서울1가1234)에서 지역을 `substr()`로 잘라 쓰는 대신 `지역` 컬럼 추가 |
| 복구용 컬럼 추가 | 고객 | 이사 후에도 이전 주소를 바로 확인할 수 있도록 `이전주소` 컬럼 추가 |

파생 컬럼은 수량이나 단가가 바뀌면 총금액을 다시 계산해야 하는 문제가 있는데, 이는 계산식으로 값을 만드는 **가상 컬럼(계산된 컬럼)**으로 해결할 수 있다.

직원당 최근 등록 차량 1대를 찾으려면 매번 아래처럼 분석 함수를 써야 하지만, `최근등록여부` 컬럼을 두면 `WHERE 등록여부 = 'Y'`로 간단히 조회할 수 있다.

```sql
SELECT 차량번호, 연식, 차종, 등록일자, 직원번호
FROM (
    SELECT 차량번호, 연식, 차종, 등록일자, 직원번호,
           ROW_NUMBER() OVER (PARTITION BY 직원번호 ORDER BY 등록일자 DESC) AS RN
    FROM 차량테이블
)
WHERE RN = 1;
```

#### 3. 테이블 반정규화

| 방법 | 설명 |
| --- | --- |
| 관계 병합 (슈퍼타입/서브타입) | 슈퍼타입과 서브타입을 조회 패턴에 맞게 합치거나 나눔 |
| 테이블 분할 | 수직 분할(컬럼 기준), 수평 분할(행 기준, 파티셔닝) |
| 테이블 추가 | 중복 테이블, 통계 테이블, 이력 테이블, 부분 테이블 추가 |

**슈퍼타입/서브타입을 테이블로 바꾸는 3가지 방법 (학생 - 학부생 / 대학원생)**

| 방법 | 구조 | 특징 |
| --- | --- | --- |
| 1:1 (One to One) | 학생 + 학부생 + 대학원생, 서브타입이 학번을 PK·FK로 가짐 | 가장 전통적이고 많이 쓰는 방법 |
| Plus Type (슈퍼 + 서브) | 학부생, 대학원생 각각에 학생의 공통 속성을 모두 포함 | 서브타입 조회 시 기본정보를 항상 같이 볼 때 유리, 전체 조회는 `UNION` 사용 |
| All in One (Single Type) | 학생 하나에 학년, 학회, 지도교수, 연구분야를 모두 포함 | 테이블은 하나지만 해당 없는 컬럼은 NULL |

**테이블 분할 (회원)**

| 분할 | 기준 | 예 |
| --- | --- | --- |
| 수직 분할 | 특정 **컬럼**에 조회가 집중될 때 컬럼 단위로 분할 | 회원 → 회원마스터(비밀번호, 접속시간) + 회원상세 / 회원인증, 회원사진 분리 |
| 수평 분할 | 특정 **행**에 조회가 집중될 때 행 단위로 분할 | 분기별 데이터를 논리적으로 나눔 (파티셔닝), 대량 데이터 조회에 유리 |

분할 여부는 데이터 모델링 → 용량 산정 → CRUD 매트릭스 → 트랜잭션 분석 순서로 어떤 테이블의 어떤 컬럼에 조회가 집중되는지 확인한 뒤 결정한다.

**이력 테이블 추가 (공급사)**

공급사의 전화번호, 메일주소, 위치정보를 각각의 이력 테이블(공급자번호 + 순번)로 분리해 세금계산서 발행 시 이전 정보를 대조할 수 있게 했다.

이력은 가끔 조회하고 최신 데이터는 항상 조회하므로, 공급사에 `최신전화번호`, `최신메일주소`, `최신위치정보`를 함께 두어 조인 없이 최신 값을 조회하도록 했다. 이력 테이블을 만드는 것도 반정규화의 일종이다.

#### 4. 복합키 vs 순번키

| 구분 | 복합키 (Composite Key) | 순번키 / 대체키 (Surrogate Key) |
| --- | --- | --- |
| 의미 | 여러 컬럼을 합쳐서 PK로 사용 | 의미 없는 자동 증가 값을 PK로 사용 |
| 예 | `PRIMARY KEY (order_id, product_id)` | `order_item_id NUMBER PRIMARY KEY` |
| 장점 | 데이터 자체가 식별자, PK가 중복 방지, 추가 컬럼 불필요, 정규화에 충실 | 단순함, JOIN 쉬움, 인덱스 작음, FK 관리 쉬움, 확장성 좋음 |
| 단점 | FK 전파, JOIN 조건 증가, PK 길어짐(인덱스 커짐), 키 값 변경 어려움 | 데이터 의미 없음, 중복 방지를 위한 UNIQUE 별도 필요 |
| 추천 | 관계 자체가 키인 경우, M:N 중간 테이블, 변경 가능성 없음 (좋아요, 수강신청) | 대부분의 테이블, 변경·확장 가능성 있음 (회원, 주문, 게시판) |

```sql
-- 복합키 단점: 자식 테이블과 JOIN 조건까지 키가 계속 따라다님
FOREIGN KEY (order_id, product_id)

ON a.order_id = b.order_id
AND a.product_id = b.product_id
```

실무에서는 PK는 순번키로 단순하게 두고, 업무 규칙은 UNIQUE 복합키로 보장하는 **"순번키 + UNIQUE 복합키"** 패턴을 가장 많이 쓴다.

```sql
order_item_id  (PK)
order_id
product_id

UNIQUE(order_id, product_id)
```

| 키 유형 | 인덱스 크기 (상대값) | JOIN 복잡도 (상대값) |
| --- | --- | --- |
| 복합키 | 80 | 75 |
| 순번키 | 30 | 20 |

FK 전파가 많은지, JOIN이 많은지, 확장이 필요한지를 기준으로 판단하며, 결론적으로 대부분 순번키 + UNIQUE 제약을 사용한다.

#### 5. 물리 모델링

| 단계 | 내용 |
| --- | --- |
| 1. 데이터 타입 설정 | 컬럼별 물리 이름, 데이터 타입, 길이, NULL 허용 여부 지정 |
| 2. 제약 추가 | UNIQUE, CHECK 제약 추가 |
| 3. 인덱스 설정 | 필요한 경우 인덱스 추가 (PK는 자동 생성) |
| 4. 스크립트 생성 | 완성된 모델로 테이블 생성 DDL 스크립트 생성 |

| 용도 | 데이터 타입 | 예 |
| --- | --- | --- |
| 번호, 순번 | NUMBER(n) | 고객번호, 거래순번 |
| 금액 | NUMBER(15) | 잔액, 거래금액 |
| 금리 | NUMBER(5,2) | 계약금리 |
| 코드, 상태, 구분 | CHAR(1), VARCHAR2(10) | 고객구분, 계좌상태 |
| 앞자리 0·하이픈이 있는 번호 | VARCHAR2 | 계좌번호, 사업자등록번호, 연락처 |
| 일자 / 순서가 중요한 일시 | DATE / TIMESTAMP | 개설일자 / 거래일시 |

물리 이름은 영어 대문자와 `_`로 짓고, PK와 업무상 반드시 필요한 값은 NOT NULL, 특정 경우에만 값이 생기는 컬럼(사업자등록번호, 탈퇴일시, 만기일자, 실패사유 등)은 NULL로 둔다.

Oracle의 `VARCHAR2(n)`은 기본적으로 바이트 단위라서 UTF-8 환경의 한글은 한 글자에 3바이트를 차지하고, `NUMBER(3)`은 0~999의 정수를 저장하므로 개월 단위 계약기간을 담기에 충분하다.

#### 6. JavaScript 비동기 (Asynchronous)

JavaScript는 한 번에 한 작업씩 위에서 아래로 실행하기 때문에, 오래 걸리는 작업이 있으면 페이지가 멈춘 것처럼 보인다.

비동기 프로그래밍은 파일 다운로드처럼 오래 걸리는 작업을 시작해 두고 결과를 기다리는 동안 다른 코드를 계속 실행한 뒤, 결과가 준비되면 그때 처리하는 방식이다.

| 순서 | 주제 | 핵심 |
| --- | --- | --- |
| 1 | Async Programming | 동기 vs 비동기, 블로킹 |
| 2 | Callbacks | 나중에 호출될 함수를 인자로 전달 |
| 3 | Promises | 비동기 작업의 미래 결과를 나타내는 객체 |
| 4 | Async / Await | Promise를 동기 코드처럼 읽기 쉽게 작성 |
| 5 | Parallel | 서로 독립적인 작업을 동시에 시작 |
| 6 | Event Loop | 단일 스레드에서 비동기 작업을 처리하는 원리 |
| 7 | Fetch | 서버에서 데이터를 가져오는 비동기 API |
| 8 | Mistakes | 비동기 코드에서 자주 하는 실수 |
| 9 | Debugging | 비동기 코드 디버깅 방법 |
| 10 | AbortController | 비동기 작업 취소 |
| 11 | Web Workers | 무거운 계산을 별도 스레드에서 실행 |
| 12 | Reference | Promise 메서드 정리 |

##### 6.1 Async Programming

| 구분 | 동기 (Synchronous) | 비동기 (Asynchronous) |
| --- | --- | --- |
| 실행 방식 | 한 줄이 끝나야 다음 줄 실행 | 오래 걸리는 작업은 백그라운드에서 진행하고 다음 코드 실행 |
| 문제 / 장점 | 긴 작업이 페이지를 막음 (Blocking) | 페이지가 멈추지 않고 응답성 유지 |

타이머(`setTimeout`), 네트워크 요청(`fetch`), 클릭 이벤트, 애니메이션(`requestAnimationFrame`) 등이 대표적인 비동기 작업이다.

비동기는 여러 작업을 번갈아 처리해 화면이 멈추지 않게 하는 것(응답성)이고, 병렬은 여러 CPU에서 동시에 실행해 더 빨리 끝내는 것(성능)으로 서로 다른 개념이다.

##### 6.2 Callbacks

콜백은 다른 함수에 인자로 전달되는 함수로, 전달받은 함수가 언제 호출할지 결정한다.

콜백 자체는 동기도 비동기도 아니며, `forEach()`, `map()`, `filter()`의 콜백은 즉시 실행되는 동기 콜백이다. `setTimeout()`, 이벤트, `fetch()` 같은 비동기 API에 전달될 때 비동기 콜백이 된다.

```js
setTimeout(function () { myDisplayer("Finished!"); }, 3000);   // 3초 후 콜백 실행
document.getElementById("myButton").addEventListener("click", displayDate);
```

함수를 인자로 넘길 때는 괄호를 붙이지 않는다. `setTimeout(myFunction, 3000)`이 맞고, `setTimeout(myFunction(), 3000)`은 즉시 실행된다.

##### 6.3 Promises

콜백이 여러 단계로 중첩되면 읽기 어려운 **콜백 지옥(callback hell)**이 생기는데, Promise는 이를 `.then()` 체인으로 평평하게 만든다.

| 상태 | 의미 |
| --- | --- |
| Pending | 작업이 시작되었지만 아직 끝나지 않음 |
| Fulfilled | 작업이 성공적으로 완료됨 |
| Rejected | 작업이 실패함 |

Fulfilled나 Rejected가 되면 settled(처리 완료) 상태라고 하며, Promise는 한 번만 settle된다.

```js
const promise = new Promise(function (resolve, reject) {
  if (success) resolve("Operation completed");
  else reject("Operation failed");
});

promise
  .then(value => myDisplayer(value))     // 성공 시
  .catch(error => myDisplayer(error))    // 실패 시 (앞 단계 어디서든 발생한 에러 처리)
  .finally(() => myDisplayer("끝"));      // 성공·실패 상관없이 실행
```

`then()`은 기다리지 않고 콜백을 등록한 뒤 바로 새 Promise를 반환하므로 체이닝이 가능하다.

##### 6.4 Async / Await

| 키워드 | 역할 |
| --- | --- |
| `async` | 함수가 항상 Promise를 반환하게 함 (일반 값을 반환해도 Promise로 감쌈) |
| `await` | Promise가 settle될 때까지 **현재 async 함수만** 일시 정지 (JavaScript 전체는 멈추지 않음) |

```js
async function getData() {
  try {
    let response = await fetch("fetch.txt");
    let text = await response.text();
    myDisplayer(text);
  } catch (err) {
    myDisplayer(err);   // rejected된 Promise는 try...catch로 처리
  }
}
myDisplayer("Start"); getData(); myDisplayer("Continue");
// 출력: Start → Continue → (다운로드 후) 텍스트
```

`await`은 async 함수 안이나 모듈 최상위에서만 쓸 수 있고, 내부적으로는 여전히 Promise를 사용한다.

##### 6.5 Parallel

`await`을 연달아 쓰면 앞 작업이 끝나야 다음 작업이 시작되므로, 서로 의존하지 않는 작업은 동시에 시작하는 것이 빠르다.

```js
const [customer, products] = await Promise.all([
  fetch("customer.json"),
  fetch("products.json")
]);
```

| 메서드 | 동작 |
| --- | --- |
| `Promise.all()` | 모두 성공하면 resolve, 하나라도 실패하면 reject |
| `Promise.allSettled()` | 성공·실패와 관계없이 모두 끝날 때까지 기다림 |
| `Promise.any()` | 가장 먼저 성공한 결과 반환 |
| `Promise.race()` | 성공·실패 상관없이 가장 먼저 settle된 결과 반환 |

##### 6.6 Event Loop

JavaScript는 한 번에 하나의 코드만 실행하고, 타이머나 네트워크 요청은 브라우저가 대신 처리한 뒤 완료되면 알려 준다.

이벤트 루프는 JavaScript가 현재 작업을 끝냈는지 계속 확인하고, 끝나면 대기 중인 다음 작업을 실행한다.

| 큐 | 들어가는 작업 | 우선순위 |
| --- | --- | --- |
| Microtask Queue | `Promise.then()`, `catch()`, `finally()`, `await` 이후 코드 | 높음 (작업 하나가 끝날 때마다 모두 먼저 처리) |
| Task Queue | `setTimeout()`, `setInterval()`, 클릭 이벤트 | 낮음 |

```js
myDisplayer("A");
setTimeout(() => myDisplayer("B"), 0);
Promise.resolve().then(() => myDisplayer("C"));
myDisplayer("D");
// 출력: A → D → C → B
```

`setTimeout(..., 0)`도 즉시 실행되지 않고 현재 코드와 마이크로태스크가 끝난 뒤 실행되며, 긴 반복문이 돌면 화면 갱신(repaint)까지 멈춘다.

##### 6.7 Fetch API

`fetch()`는 서버에 데이터를 요청하는 비동기 메서드로, Response 객체로 resolve되는 Promise를 반환한다.

| Response 속성 / 메서드 | 설명 |
| --- | --- |
| `ok` | 요청 성공 여부 (true / false) |
| `status`, `statusText` | HTTP 상태 코드와 메시지 (200, 404 등) |
| `text()`, `json()`, `blob()` | 응답 본문을 텍스트, JSON 객체, 바이너리로 읽음 |

```js
async function loadCustomer() {
  const response = await fetch("customer.json");
  const customer = await response.json();
  myDisplayer(customer.name);
}
```

##### 6.8 Async Mistakes

| 실수 | 올바른 방법 |
| --- | --- |
| `await`을 빠뜨림 → 데이터 대신 Promise를 받음 | `const response = await fetch(url)` |
| 일반 함수 안에서 `await` 사용 | 함수 앞에 `async` 붙이기 |
| 404면 `fetch()`가 실패한다고 생각함 | HTTP 에러는 reject되지 않으므로 `response.ok` 확인 |
| 콜백이면 비동기라고 생각함 | 비동기 여부는 `setTimeout` 같은 API가 결정 |
| 독립적인 요청을 하나씩 `await` | `Promise.all()`로 동시에 시작 |
| `forEach` 안에서 `await` | `forEach`는 기다리지 않으므로 `for...of` 사용 |
| 에러 처리 누락 | `try...catch` 또는 `.catch()` 사용 |

##### 6.9 Async Debugging

비동기 디버깅은 "어디서 멈췄는지" 찾고 "왜 멈췄는지" 확인하는 과정이다.

`console.log()`로 실행 순서를 기록하고, `try...catch`로 네트워크·JSON 파싱 에러를 잡으며, `response.ok`로 HTTP 에러를 따로 구분한다.

비동기 에러는 함수가 이미 반환된 뒤에 발생할 수 있어 "아무 일도 안 일어난 것처럼" 보이므로, 에러 처리를 항상 넣어야 한다.

##### 6.10 AbortController

```js
const controller = new AbortController();
fetch("largefile.txt", { signal: controller.signal })
  .catch(err => { if (err.name === "AbortError") myDisplayer("Download canceled"); });

controller.abort();   // 요청 취소
```

취소 버튼, 새 검색어 입력, 페이지 이탈, 시간 초과(`setTimeout`과 함께 사용) 등 더 이상 필요 없는 요청을 취소할 때 사용한다.

한 번 abort된 컨트롤러는 재사용할 수 없으므로 요청마다 새로 만들어야 한다.

##### 6.11 Web Workers

Promise나 async/await도 결국 메인 스레드에서 실행되므로, 오래 걸리는 계산은 여전히 페이지를 멈추게 한다.

Web Worker는 JavaScript를 **별도 스레드**에서 실행해 메인 스레드가 사용자 입력에 계속 응답할 수 있게 하며, 메인과 워커는 메시지로 통신한다.

```js
// main
const worker = new Worker("worker.js");
worker.onmessage = event => myDisplayer(event.data);
worker.postMessage(25);

// worker.js
onmessage = event => postMessage(event.data * event.data);   // 625
```

##### 6.12 Promise Reference

| 구분 | 메서드 |
| --- | --- |
| 생성자 | `new Promise(executor)` |
| 인스턴스 메서드 | `then()`, `catch()`, `finally()` |
| 정적 메서드 | `Promise.resolve()`, `Promise.reject()`, `Promise.all()`, `Promise.allSettled()`, `Promise.any()`, `Promise.race()`, `Promise.try()`, `Promise.withResolvers()` |

#### 7. UML 다이어그램

UML은 14개의 다이어그램이 있으며, 시스템 분석·설계에서는 그중 자주 쓰이는 다이어그램을 중심으로 활용한다.

| 다이어그램 | 설명 |
| --- | --- |
| **유스케이스** | 액터가 시스템으로 달성하려는 목표와 시스템이 제공할 기능 |
| 활동 | 업무·활동의 흐름과 조건 (순서도와 유사, 스윔레인으로 주체 구분) |
| **클래스** | 클래스와 클래스 간 관계로 시스템의 정적 구조 표현 |
| 객체 | 특정 시점의 객체와 속성값을 스냅샷으로 표현 |
| **시퀀스** | 객체들이 주고받는 메시지를 시간 순서대로 표현 |
| 커뮤니케이션 | 시퀀스와 같은 상호작용을 객체 간 연결 구조 중심으로 표현 |
| 상태 머신 | 객체의 상태와 상태를 바꾸는 이벤트, 수명 주기 |
| 컴포넌트 | 소프트웨어 컴포넌트 구조와 의존성 |
| 배치 | 하드웨어 노드에 소프트웨어 아티팩트가 배치되는 물리 구조 |
| 패키지 | 패키지(모듈) 간 구조와 의존성 |
| 복합 구조 | 클래스나 협업의 내부 구조 |
| 프로필 | 스테레오타입 정의 |
| 상호작용 개요 | 여러 상호작용(시퀀스)의 제어 흐름 개요 |
| 타이밍 | 시간에 따른 객체 상태 변화 (시간축이 왼쪽 → 오른쪽) |

##### 7.1 유스케이스 다이어그램 ⭐

사용자(액터)가 목표를 달성하기 위해 시스템과 어떻게 상호작용하는지, 시스템이 어떤 기능을 제공해야 하는지를 표현한다.

| 구성 요소 | 설명 | 표기 |
| --- | --- | --- |
| 액터 (Actor) | 시스템 외부에서 상호작용하는 **역할** (사람, 조직, 외부 시스템), 명사로 표현 | 사람 모양 |
| 유스케이스 (Use Case) | 액터의 목표를 위해 시스템이 제공하는 기능, **동사 + 명사**로 표현 (수강 신청하기) | 타원 |
| 시스템 경계 (System Boundary) | 개발 대상 시스템의 범위, 유스케이스는 안쪽, 액터는 바깥쪽 | 사각형 |
| 연관 (Association) | 액터와 유스케이스의 상호작용 | 실선 |

| 관계 | 의미 | 표기 / 화살표 방향 | 예 |
| --- | --- | --- | --- |
| 포함 (Include) | 다른 기능을 **반드시** 포함해 수행, 공통 기능 재사용 | 점선 + `<<include>>`, 기본 → 포함되는 유스케이스 | 주문하기 → 로그인하기 |
| 확장 (Extend) | **특정 조건**에서만 기능 추가 | 점선 + `<<extend>>`, 확장 → 기본 유스케이스 | 쿠폰 적용하기 → 결제하기 |
| 일반화 (Generalization) | 일반적인 기능·액터를 구체적인 유형으로 특수화 | 실선 + 빈 삼각형, 자식 → 부모 | 지문 확인 / ID 카드 확인 → 신원 확인 |

로그 저장, 데이터 백업처럼 액터의 목표와 직접 관련 없는 내부 처리는 별도의 유스케이스로 만들지 않는다.

##### 7.2 시퀀스 다이어그램 ⭐

특정 시나리오에서 객체들이 주고받는 메시지를 **시간 순서(위 → 아래)**로 표현하며, 유스케이스의 시나리오가 객체 협력으로 어떻게 수행되는지 상세히 모델링할 때 유용하다.

| 구성 요소 | 설명 |
| --- | --- |
| 객체 / 액터 | 상단에 왼쪽에서 오른쪽으로 배치 |
| 라이프라인 (Lifeline) | 객체 아래로 이어지는 점선, 시나리오에 참여하는 참가자 |
| 활성화 (Activation) | 라이프라인 위의 얇은 직사각형, 객체가 작업을 수행하는 기간 |
| 메시지 (Message) | 라이프라인 사이의 가로 화살표, 세로 위치가 실행 순서 |

| 메시지 | 표기 | 의미 |
| --- | --- | --- |
| 동기 (호출) | 실선 + 채워진 화살촉 | 응답을 받을 때까지 기다리는 일반적인 호출 |
| 비동기 | 실선 + 열린 화살촉 | 수신자의 작업 완료를 기다리지 않음 |
| 리턴 | 점선 + 열린 화살촉 | 호출 결과 반환 |
| 셀프 / 재귀 | 자기 자신에게 돌아오는 화살표 | 같은 객체의 다른 작업이나 재귀 호출 |
| 생성 / 소멸 | create / destroy | 상호작용 중 객체 생성, 소멸 |

반복은 `* [for all order lines]`처럼 `*`와 조건으로 표시한다.

##### 7.3 클래스 다이어그램 ⭐

클래스와 클래스 간의 관계로 객체지향 시스템의 **정적 구조**를 표현한다.

| 영역 | 내용 | 예 |
| --- | --- | --- |
| 1칸: 클래스 이름 | 필수 | `Order` |
| 2칸: 속성 | 멤버 변수, `이름 : 타입` | `- orderNo : int` |
| 3칸: 연산 | 메서드, `이름(매개변수 : 타입) : 반환타입` | `+ addItem(item : Item) : void` |

가시성은 `+`(public), `-`(private), `#`(protected)로 표시한다.

| 관계 | 의미 | 표기 | 예 |
| --- | --- | --- | --- |
| 일반화 (상속) | is-a 관계 | 실선 + 빈 삼각형 (자식 → 부모) | 개 → 동물 |
| 실체화 | 인터페이스 구현 | 점선 + 빈 삼각형 (구현 클래스 → 인터페이스) | Person → Owner |
| 연관 | 객체 간 구조적 연결, 다중성 표시 | 실선 | 학생 ─ 수강한다 ─ 과목 |
| 집합 (Aggregation) | 전체-부분, 부분이 **독립적으로 존재 가능** | 빈 마름모 ◇ (전체 쪽) | 부서 ◇─ 직원 |
| 합성 (Composition) | 전체-부분, 전체가 삭제되면 **부분도 함께 삭제** | 채워진 마름모 ◆ (전체 쪽) | 주문 ◆─ 주문항목 |
| 의존 (Dependency) | 매개변수·지역 변수 등으로 일시적으로 사용 | 점선 + 열린 화살표 | Person ⇢ Book |

클래스 다이어그램은 도메인 개념을 표현하는 개념적 관점, 인터페이스 중심의 명세 관점, 실제 구현 세부 사항까지 담는 구현 관점으로 해석할 수 있다.

#### 핵심 정리

- 반정규화는 정규화 이후 조회 성능을 위해 중복을 허용하고 조인 수를 줄이는 과정이며, 무결성 관리 방법도 함께 설계해야 한다.
- 컬럼 반정규화에는 중복 컬럼, 파생 컬럼, 이력 컬럼, PK 분리, 복구용 컬럼 추가가 있다.
- 파생 컬럼의 무결성 문제는 가상 컬럼(계산된 컬럼)으로 해결할 수 있다.
- 슈퍼타입/서브타입은 1:1, Plus Type, All in One 방식으로 테이블화하며 조회 패턴에 따라 선택한다.
- 테이블 분할은 컬럼 기준의 수직 분할과 행 기준의 수평 분할(파티셔닝)이 있다.
- 복합키는 의미가 분명하지만 FK 전파와 JOIN이 복잡해지고, 순번키는 단순하지만 UNIQUE로 중복을 따로 막아야 한다.
- 실무에서는 "순번키 + UNIQUE 복합키" 패턴을 가장 많이 사용한다.
- 물리 모델링은 데이터 타입 설정 → 제약 추가 → 인덱스 설정 → 스크립트 생성 순서로 진행한다.
- JavaScript 비동기는 오래 걸리는 작업을 기다리는 동안 다른 코드를 실행해 페이지가 멈추지 않게 하며, Callback → Promise → async/await 순으로 발전했다.
- `await`은 현재 async 함수만 멈추고, 독립적인 작업은 `Promise.all()`로 동시에 시작한다.
- 이벤트 루프는 Microtask Queue(Promise)를 Task Queue(setTimeout)보다 먼저 처리한다.
- `fetch()`는 404 같은 HTTP 에러에서 reject되지 않으므로 `response.ok`를 확인해야 한다.
- 유스케이스 다이어그램은 액터·유스케이스·시스템 경계와 Include(필수), Extend(조건부), Generalization(특수화) 관계로 기능 요구사항을 표현한다.
- 시퀀스 다이어그램은 라이프라인과 메시지로 객체 간 상호작용을 시간 순서대로 표현한다.
- 클래스 다이어그램은 이름·속성·연산과 일반화, 실체화, 연관, 집합, 합성, 의존 관계로 정적 구조를 표현한다.

</br>첫 번째 ERD에서는 거래내역이 계좌번호 + 거래순번 복합키라서 다른 테이블이 거래를 참조하려면 두 컬럼을 모두 가져가야 했지만, 이번에는 거래에 거래번호라는 순번키를 두어 이체가 출금거래번호와 입금거래번호 하나씩만으로 거래를 참조할 수 있었다.
</br>오늘 배운 복합키와 순번키의 차이가 이렇게 FK 전파와 JOIN 조건의 차이로 바로 나타나는 것을 보며, 실무에서 왜 대부분 순번키에 UNIQUE 제약을 함께 쓰는지 이해할 수 있었다.
</br>반정규화도 결국 조회 성능과 무결성 사이에서 균형을 잡는 선택이라, 정규화와 키 설계를 먼저 탄탄히 하고 실제 조회 패턴을 근거로 중복을 허용해야 한다는 것을 느꼈다.
