# 90일차

## SpaceLink 기획안과 데이터 구조 수정·정리

📌 학습일 : 2026.11.13

📌 학습 내용 : Final Project, Service Planning, Integrated Map, External Application Link, ERD Simplification, Real-time API, Redis Cache, Terms Versioning, Vehicle Data Modeling, Data Retention

---

#### 1. 어제 기획안과 비교해 달라진 점

- 어제는 서비스 범위와 역할 분담, 요구사항, 화면설계서의 큰 틀을 정리했다. 오늘은 실제 사용자 흐름과 저장할 데이터의 기준을 더 구체화했다.
- 어제 화면설계서에는 33개 화면 ID가 정리되어 있었고, 오늘 기획안에는 여기에 **PROP_MAP-01 매물 지도**를 추가하는 내용이 들어갔다.
- 오늘 작업 폴더에는 기획안, 테이블 목록, 요구사항 정의서가 있었으며, 11월 12일 작업 폴더에는 화면설계서도 포함되어 있었다. 오늘 기획안에서 화면 추가를 계획했으므로 화면설계서에도 같은 화면과 요구사항을 연결할 필요가 있다.
- 일반 집·상가·오피스 매물도 상세 화면에서 해당 매물의 신청 페이지로 이동하게 하고, 공공 공고는 공급기관 공식 신청 페이지, 공매는 온비드 입찰 페이지로 연결하도록 정리했다.

#### 2. 매물 지도를 독립 화면으로 추가

- 집·상가·오피스와 공매 매물, 현재 모집 중인 청약·공공 공고를 한 화면의 지도에 핀으로 표시한다.
- 상단 메뉴에 독립 진입점을 두고, 유형별 필터·지도 범위 검색·마커 클러스터를 제공한다.
- 사용자가 핀을 누르면 해당 매물이나 공고의 상세 화면으로 이동한다.
- 기존 청약 목록의 지도와 통합 매물 지도는 목적이 달라 각각 유지한다. 청약 목록 지도는 청약만 찾을 때 쓰고, 매물 지도는 여러 유형의 매물과 공고를 함께 살펴볼 때 쓴다.

매물 지도는 단순히 화면에 지도를 하나 더 넣는 일이 아니었다. 각 데이터의 좌표, 유형, 모집·입찰 상태와 상세 화면으로 가는 식별자를 한 지도에서 함께 다룰 수 있어야 했다. 그래서 화면 기능과 데이터 연결 기준을 함께 생각해야 한다는 점을 확인했다.

#### 3. 매물 상세의 신청 경로를 유형별로 구분

| 대상 | 상세 화면에서 연결할 곳 |
| --- | --- |
| 일반 집·상가·오피스 매물 | 해당 매물의 외부 신청 페이지 |
| 공공 상가·오피스 공고 | 공급기관의 공식 공고·신청 페이지 |
| 공매 물건 | 온비드 입찰 페이지 |

- 신청 URL이 없거나 접수 기간이 아니면 현재 상태와 확인 경로를 안내한다.
- SpaceLink는 정보를 추천하고 외부 페이지로 연결하지만, 자체 신청·중개·계약을 처리하지 않는다.
- 외부 신청 페이지는 데이터 수집 단계에서 연결 정보를 확보하고 상세 화면에서 제공해야 하므로, 단순한 버튼 디자인만으로 끝나는 기능이 아님을 정리했다.

#### 4. 데이터 저장과 실시간 조회를 나누어 ERD를 단순화

- 오늘 테이블 목록은 총 **55개**로 정리되었다. 건물 호실 정보와 공매 회차별 입찰 정보는 별도 테이블에 전부 적재하지 않고, 상세 조회 시 외부 API를 호출한 뒤 Redis에 캐시하는 방향이다.
- 반면 지도 검색, 목록 표시, 추천처럼 반복 조회와 상태 추적이 필요한 공고·건물의 기본 데이터는 DB에 저장하는 구조를 유지한다.
- 외부 데이터가 변경되거나 수집 결과에서 일시적으로 누락될 수 있으므로, 매번 조회 결과만으로 기존 DB 데이터를 삭제하지 않고 갱신·종료·삭제 기준을 구분해야 한다.
- 약관 본문은 서비스가 직접 관리하고, 내용이 바뀌면 기존 행을 덮어쓰기보다 새 버전으로 추가한다. 가입 화면은 현재 시행 중인 버전을 보여 주고, 회원 동의·철회도 이력으로 남긴다.
- 행동 기록은 원문 질문을 저장하지 않고, AI 검색·상담 대화는 저장하지 않는다는 원칙도 데이터 보관 기준에 반영했다.

외부 API를 쓴다는 이유만으로 모든 데이터를 실시간으로만 가져오는 것이 항상 좋은 것은 아니다. 최신성이 중요한 상세 정보는 실시간 호출과 캐시를 활용하고, 여러 기능이 반복해서 참조하는 핵심 데이터는 DB에 저장하는 식으로 성격에 맞게 나누는 것이 중요하다는 점을 배웠다.

#### 5. 차량 수와 차량기준가액을 차량별로 관리

- 청약 프로필에 차량 대수와 전체 차량 기준가액을 한 숫자로만 넣으면 차량이 여러 대일 때 각 차량의 소유자·가액·제외 여부를 구분하기 어렵다.
- 그래서 세대 차량은 `SUBSCRIPTION_CAR`에 **차량 1대당 1행**으로 저장하고, 소유자·차량기준가액 구간·제외 차량 여부를 각각 관리한다.
- 차량 대수는 별도 입력값으로 중복 저장하지 않고 차량 행의 개수에서 계산할 수 있다.
- 실제 자격 판단은 공고별 기준과 차량 제외 조건을 적용해야 하므로, 여러 차량의 가액을 무조건 합산하거나 임의로 결론 내리지 않고 해당 공고 규칙을 확인하는 것으로 정리했다.
- 차량 기준가액을 모른다는 선택지는 두지 않고, 보유 차량이 있으면 각 차량의 가액 구간을 입력하도록 했다.

#### 6. 핵심 정리

- 어제 정리한 화면 구성에 통합 매물 지도 화면을 추가하고 청약 목록 지도와 구분했다.
- 집·상가·오피스 매물, 공공 공고, 공매의 신청·입찰 경로를 상세 화면에서 각각 올바른 외부 페이지로 연결한다.
- 55개 테이블 설계에서 핵심 데이터는 저장하고, 변경이 잦거나 상세 시 필요한 호실·입찰 정보는 실시간 호출과 Redis 캐시로 다루도록 구분했다.
- 약관은 버전과 회원 동의 이력을 저장하며, 차량은 대수 숫자 대신 차량별 행으로 설계한다.

---

오늘 가장 중요하게 배운 점은 **DB에 무엇을 저장할지 결정할 때 화면과 실제 업무 규칙을 같이 봐야 한다는 것**이다. 자동차 대수만 저장하면 각 차량의 기준가액을 제대로 표현하기 어렵고, 반대로 외부 API의 모든 상세값을 테이블로 만들면 관리해야 할 데이터가 과도해질 수 있다. 차량은 한 대씩 구분해 저장하고, 최신성이 중요한 상세 정보는 필요할 때 호출해 캐시하는 식으로 데이터의 성격에 맞는 구조를 선택해야 한다.
</br>또한 매물 지도를 추가하면서 화면 하나의 요구가 좌표·유형·상태·상세 연결까지 이어진다는 점을 확인했다. 화면설계서와 요구사항, ERD가 서로 따로 움직이면 구현 단계에서 빠지는 기능이 생길 수 있으므로, 변경된 기획을 다른 산출물에도 함께 반영해야 한다고 느꼈다.

어제는 프로젝트의 큰 틀을 문서로 맞추는 데 집중했다면, 오늘은 사용자가 실제로 어디로 이동하고 각 정보가 어디서 오며 얼마나 저장되는지를 구체적으로 따져 보았다. 앞으로도 데이터가 바뀌는 경우와 조회할 수 없는 경우까지 생각해 설계하고, 확정된 기능은 기획서·요구사항·화면설계서·ERD에 같은 기준으로 반영해야겠다.
