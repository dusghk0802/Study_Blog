#### 1. 여러 공공 API의 수집 흐름을 공통화했다

API마다 페이지를 읽고 응답을 바꾸고 저장하는 코드를 따로 만들면 같은 오류 처리와 재시작 처리가 반복된다. 이를 줄이기 위해 페이지 단위로 응답을 읽는 `PagedApiReader`, 공공데이터 응답을 변환하는 `DataGoKr`, 네트워크 오류를 다시 시도하는 `Retry`, 공통 Step을 만드는 `CollectSteps`를 추가했다.

청약홈 수집기를 공통 페이지 구조로 옮기고, 마이홈·LH 공고·실거래 수집 Job을 추가했다. 수동 실행 API도 Job별 경로로 실행하도록 일반화하고, 매일 실행되는 수집 일정과 최근 수집 범위를 공통 설정으로 묶었다.

| 구성 | 역할 |
| --- | --- |
| `PagedApiReader` | 페이지를 한 건씩 읽고 실행 위치를 저장해 재시작 지원 |
| `DataGoKr` | 공공데이터 JSON·XML 응답을 공통 페이지 데이터로 변환 |
| `Retry` | 네트워크 오류와 서버 오류 발생 시 API 요청 재시도 |
| `CollectSteps` | 읽기·변환·저장 및 건별 오류 처리를 공통 Step으로 구성 |
| Job 실행 API·스케줄러 | 공고 수집을 수동 또는 매일 자동 실행 |

공고 저장에서는 출처와 원본 공고 ID로 기존 행을 찾아 갱신하고, 신규·정정 공고의 일정과 좌표를 처리하도록 흐름을 정리했다. XML 응답 지원과 HTTP 연결·응답 시간 설정도 추가했다.

#### 2. LH 공고 상태를 실제 API 기준으로 검토했다

승인된 LH 분양임대공고문 조회 API를 실제 호출해 응답을 확인하고, 기능 호출 경로를 명세의 서비스 기본 주소와 구분했다. 테스트 DB에서 수집 결과를 확인한 뒤, 임시 테스트 DB와 볼륨은 삭제했다.

코드 검토 중 LH가 `PAN_SS=접수마감`으로 반환한 공고가 우리 시스템에서는 접수 중으로 계산될 수 있는 문제를 발견했다. 기존 매핑이 공고게시일을 접수 시작일로, `CLSG_DT` 공고마감일을 접수 종료일로 간주했기 때문이다. 공고를 게시한 기간과 실제 신청을 받는 기간은 같은 의미가 아니다.

| 값 | 처리 기준 |
| --- | --- |
| `PAN_SS=공고중` | 내부 상태 `UPCOMING`으로 처리 |
| `PAN_SS=접수중` | 내부 상태 `OPEN`으로 처리 |
| `PAN_SS=접수마감` | 내부 상태 `CLOSED`로 저장하고 화면 목록에서 제외 |
| `PAN_SS=상담요청`·`정정공고중` | 현재 사례가 없어 보수적으로 `UPCOMING` 처리 |
| `PAN_NT_ST_DT` | 공고게시일로만 사용 |
| `CLSG_DT` | 공고마감일로 사용하고, 지난 경우 마감 처리 안전장치로 사용 |
| 공고문에서 추출한 실제 접수일 | 추출 전까지 미확정으로 두고 D-day·마감 임박 정렬에 사용하지 않음 |

상태가 늦게 바뀌어 DB에 남지 않는 일을 방지하기 위해 LH는 매일 최근 1년 데이터를 다시 조회하기로 했다. 마감 공고도 DB에는 저장·갱신하고, 모집 중·모집 예정만 노출하는 것은 Web 목록 조회에서 처리한다. 이 기준은 오늘 확정한 처리 방향이며, 게시일을 접수일로 매핑한 코드는 후속 수정이 필요하다.

#### 3. 사전청약 API를 현재 서비스 범위에서 제외했다

사전청약 API의 응답과 상세 API 호출 조건을 검토했다. 확인한 응답에서는 지역 코드가 비어 있거나 지역명이 `전국`으로 제공되어 서울 공고를 안정적으로 판별하기 어려웠다. 하나의 공고에 여러 지구가 함께 들어갈 수 있어 공고 하나를 하나의 지도 좌표로 표현하는 것도 부정확하다.

상세정보 API는 공급정보구분코드와 고객센터연계시스템구분코드 등 목록 응답에서 확인되지 않은 값을 요구한다. 사전청약 공고는 현재 SpaceLink의 서울 지역·위치 기반 탐색 범위에 맞지 않으므로 수집 대상에서 제외하기로 했다. 이 결정을 반영해 기획서 14장 API 목록에서 LH 사전청약 항목을 삭제했다.

#### 4. API 명세와 아키텍처 자료를 정리했다

API 명세서 원본에는 승인된 LH 분양임대공고문 조회 서비스를 `GOV-022`로 추가했다. API 기본 주소와 기능 호출 경로, 인증 환경변수, 요청 파라미터와 응답 필드를 구분해 기입했다. 실제 인증키 값은 명세에 넣지 않고 `.env`에서 읽도록 했다.

#### 5. 배치 테스트로 변경 구조를 확인했다

페이지 응답 변환, 공고 매핑, 일정 저장 등 배치 모듈 테스트를 실행해 `BUILD SUCCESSFUL`을 확인했다. 테스트 DB에서는 LH 공고 수집 결과도 확인하고, 검증이 끝난 테스트 전용 DB는 제거했다.

#### 핵심 정리

- 여러 API의 공통 페이지 읽기·응답 변환·재시도·저장 흐름을 공통 배치 구조로 묶었다.
- LH의 공고 상태는 `PAN_SS`로 판정하고, 게시일·공고마감일을 실제 접수 기간으로 오해하지 않아야 한다.
- LH 공고 상태가 갱신되도록 최근 1년치를 매일 재수집하고, 마감 공고는 저장하되 화면 목록에서 제외한다.
- 공고문에서 실제 접수 기간을 추출하기 전에는 미확정으로 두고 일정 계산에 사용하지 않는다.
- 지역과 좌표를 특정하기 어려운 사전청약 API는 현재 서울 기반 서비스 범위에서 제외하고 기획서 목록에서도 제거했다.
- 테스트 DB는 검증 후 삭제하고, 개발 DB와 구분해 관리한다.

---

오늘은 API를 호출해 데이터를 받는 것만으로 수집 기능이 완성되는 것은 아니라는 점을 배웠다. API 필드가 비슷해 보여도 공고게시일·공고마감일과 실제 접수 일정은 서로 다른 업무 의미를 가진다. 이를 잘못 연결하면 이미 접수가 끝난 공고가 신청 가능한 것처럼 표시될 수 있다.

또한 원본 상태값을 우선 활용하고, 날짜는 실제 의미가 확인된 경우에만 상태 계산에 사용해야 한다는 점을 확인했다. LH처럼 상태가 나중에 바뀌는 데이터는 재수집 주기도 데이터 정확성의 일부다. 최근 기간을 너무 짧게 잡으면 오래된 공고의 상태 변경을 놓칠 수 있다.

사전청약은 API가 제공하는 값만으로 위치를 단정하면 지도와 추천 결과가 왜곡될 수 있었다. 기능을 추가하는 것보다 서비스 범위와 데이터가 실제로 뒷받침하는 기능을 맞추는 것이 중요하다고 느꼈다. 다음에는 오늘 발견한 LH 접수일 매핑 오류를 확정한 기준대로 코드와 테스트에 반영해야겠다.
