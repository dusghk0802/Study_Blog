# 93일차

## SpaceLink 기획·요구사항·화면설계·WBS 정합성 점검

📌 학습일 : 2026.11.17

📌 학습 내용 : 서비스 범위 구체화, 공공기관 모의 조회, 화면 ID 추적성, 매물 지도, 공식 신청 링크, 역할 분담, WBS, 개인정보 보호, 통합 테스트

---

#### 1. 어제 학습일지와 비교해 달라진 점

- 92일차에는 Docker Compose로 Spring Boot와 MySQL 실행 환경을 구성하고, 이미지·컨테이너·네트워크·환경 변수의 역할을 확인했다.
- 93일차에는 실행 환경보다 프로젝트 문서 간 기능 범위와 구현 책임을 맞추는 데 집중했다. 기획서, 요구사항 정의서, 화면설계서에 흩어진 기능을 서로 연결하고, 실제 개발 순서와 담당자까지 WBS에 반영했다.
- 특히 기능 이름만 나열하지 않고 “사용자가 어디서 시작해 어떤 결과를 받고, 어느 화면이나 외부 페이지로 이동하는가”를 기준으로 흐름을 정리했다.

#### 2. SpaceLink의 서비스 범위와 화면 구조 정리

- 집·상가·오피스 화면이 모두 일반 중개 매물을 직접 등록하거나 계약하는 서비스처럼 보이지 않도록 범위를 분명히 했다. 청약·공공 공고와 공매 물건은 목록과 상세에서 안내하고, 실제 신청은 청약홈·공급기관의 공식 페이지로, 입찰은 온비드로 이동한다.
- 집·상가·오피스 상세는 기본 정보, 가격, 추천 점수, 주변 환경, 위험 정보 등 공통 구성을 사용한다. 대상별로 맞지 않는 정보는 ‘해당 없음’ 또는 ‘확인 필요’로 표현하고, 공공 공고나 공매 물건에만 외부 신청·입찰 버튼을 보여 준다.
- 모집 중인 청약·공공 공고와 집·상가·오피스·공매 물건을 한 지도에 표시하는 `PROP_MAP-01 매물 지도`를 독립 화면으로 정리했다. 유형 필터, 지도 범위 검색, 클러스터, 핀 선택 후 상세 화면 이동을 포함한다. 청약 목록의 지도와 전체 매물을 보는 지도의 목적을 구분했다.
- 화면설계서에는 로그인, 계정 찾기, 찾는 대상 설정, 매물 지도, 후보 비교, 알림함, 안내·오류, 관리자 화면 등 세부 화면 ID를 연결해 화면 단위의 요구사항을 추적할 수 있게 했다.

#### 3. 청약 프로필을 기관별 모의 조회 흐름으로 구체화

- 사용자가 청약 조건을 직접 여러 항목으로 판단해 입력하는 방식 대신, 기관과 요청 자료를 고르고 동의·간편인증을 거쳐 기관별 조회 결과를 확인하고 저장하는 흐름으로 정리했다.
- 행정안전부의 거주·세대 정보, 가족관계 자료, 국세청·건강보험·고용보험의 소득 자료, 주택·자동차 정보, 청약통장과 당첨 이력처럼 정보별 출처와 실제 확인이 필요한 범위를 표로 구분했다.
- 현재 시연에서는 실제 기관에 요청하지 않고 서버가 가상 응답을 반환한다. 기관별 완료·실패·결과 없음 상태, 실패 항목 재조회, 조회 결과 확인과 저장을 구현해 실제 연계 전에도 사용자 흐름과 판정 로직을 검토할 수 있게 했다.
- 원문 응답이나 증빙 파일을 통째로 저장하지 않고, 자격 판단에 필요한 정규화 값만 저장하는 방향을 확인했다. 실제 연계 가능 항목, 정보주체 동의 범위, 기관 승인 여부는 확인 전까지 확정값처럼 다루지 않는다.
- 이 설계는 가입과 청약 정보 조회를 분리하고, 청약 프로필의 민감 정보가 AI로 전달되지 않도록 하는 개인정보 보호 원칙과도 연결된다.

#### 4. 추천·지도·찜 기능의 연결 관계 정리

- 메인 AI 검색은 자연어 질문을 조건으로 바꾸고, 조회 도구가 공고와 매물을 찾은 뒤 추천 결과와 이유를 화면에 보여 주는 구조로 정리했다. AI 고객상담은 사이트 이용 문의만 다루고 청약 자격 판단과는 분리한다.
- AI 검색·추천과 AI 고객상담의 대화는 DB에 저장하지 않는다. 사용자가 페이지에 있는 동안만 대화 상태를 유지하고 페이지를 벗어나면 초기화한다. 다시 보고 싶은 결과는 대화 기록 대신 찜으로 저장한다.
- 찜은 상세 화면에서 등록·해제한 결과가 마이페이지 목록에 이어지도록 하고, 후보 비교는 그 목록을 사용한다. 이연화 담당 범위에는 후보 비교 API·화면과 AI 추천 이유를 명시하고, 정려립 담당 범위에는 찜과 마이페이지 연동을 명시했다.
- 통합 지도, 공식 신청·입찰 링크, 후보 비교 지도까지 구현·검증 범위에 넣어 기능 간 연결이 끊기지 않도록 했다.

#### 5. 요구사항과 WBS를 실제 구현 책임에 맞춤

- 요구사항 정의서는 기관별 청약 정보 조회의 시작·완료·실패 기준, 결과 저장·재조회, 관련 화면 ID를 연결한다. 요구사항의 완료 기준을 구체화하면 “화면이 보이는 것”과 “기능 흐름이 동작하는 것”을 구분해 확인할 수 있다.
- WBS에서는 정려립이 기관 모의 조회 화면, 매물 찜·마이페이지 연동, 관리자 전체 화면, 고객센터·문의·AI 상담 화면을 맡도록 반영했다. 이연화는 조회 응답 Mock·API, 매물 지도, 외부 신청·입찰 링크, 후보 비교 API와 AI 추천 이유를 맡도록 정리했다.
- 테스트도 담당 기능별로 구체화했다. 이연화는 조회·자격·추천·지도·공식 링크·후보 비교 API를 확인하고, 정려립은 모의 조회부터 찜·마이페이지, 관리자·문의 화면까지 담당 흐름을 확인한다. 4주차에는 오류 수정과 회귀 확인, 배포와 시연 리허설을 진행한다.
- 일정은 선행 기능을 기준으로 잡아, 매물 상세가 구현되기 전에 찜 연동을 검증하는 식의 순서 오류가 생기지 않도록 했다. 화면에서 상세 데이터를 확인할 수 있어야 찜 등록·해제와 마이페이지 반영을 검증할 수 있다.

#### 6. 문서 정합성 점검에서 배운 점

- 기획서에는 32개 화면 ID라고 적혀 있지만, 요구사항 정의서의 미결사항에는 화면 ID 33개와 PDF 29페이지의 매핑 확인이 남아 있다. 숫자가 다르면 어느 화면이 빠졌는지 알기 어렵기 때문에 화면 ID 목록과 최종 산출물의 대응표를 확정해야 한다.
- 개발 일정도 기획서 1절의 기간과 15절 일정표의 기간이 다르게 적혀 있어 최종 기준을 맞춰야 한다. 역할을 WBS에 반영할 때는 화면 목록·요구사항 담당자 표기와 함께 확인해야 이후 인수인계와 테스트에 혼선이 줄어든다.
- 기능을 수정할 때 한 문서만 고치는 것으로 끝나지 않는다. 같은 기능이 서비스 소개, 기능표, 입력 정보, 화면 명세, 요구사항, 담당자, 일정에 각각 등장하므로 영향 범위를 함께 점검해야 한다.

#### 7. 핵심 정리

- 실제 공공기관 연계가 없는 단계에서도 기관별 모의 응답과 상태 흐름을 만들면 조회·실패·재시도·저장 절차를 검증할 수 있다.
- 공식 신청·입찰은 SpaceLink 내부에서 처리하지 않고 외부 기관 페이지로 연결한다. 이 경계를 문서와 화면에 같이 적어야 사용자가 서비스를 오해하지 않는다.
- 매물 지도, 찜, 마이페이지, 후보 비교, AI 추천은 각자 독립된 기능이 아니라 데이터가 이어지는 사용자 흐름이다.
- WBS는 업무 목록이 아니라 선행 관계, 담당자, 완료 기준, 테스트 범위를 함께 보여 주는 실행 계획이다.

---

오늘 가장 크게 배운 점은 기획·요구사항·화면·일정표가 같은 서비스 흐름을 서로 다른 관점에서 설명해야 한다는 것이다. 기관 모의 조회를 화면에 추가하면 조회 API의 가상 응답, 저장할 값, 실패 재시도, 개인정보 처리, 테스트와 담당자까지 함께 결정해야 한다. 그 연결이 빠지면 문서에는 기능이 있어도 구현 순서와 완료 기준이 모호해진다.

또한 화면 수나 개발 기간처럼 기본적인 숫자도 문서마다 다르면 팀이 서로 다른 계획을 보고 작업할 수 있다는 점을 확인했다. 앞으로는 기능을 추가할 때 관련 화면 ID와 요구사항 ID를 따라가며 변경 범위를 점검하고, 미결사항은 확정된 내용처럼 쓰지 않아야겠다. 오늘 WBS를 수정하며 담당자와 선행 기능을 명확히 적는 것이 일정표를 실제 협업 도구로 만드는 핵심이라고 느꼈다.
