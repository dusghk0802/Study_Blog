#### 1. 온비드 수집 결과를 테스트 DB에서 검증했다

온비드 부동산 물건 목록 API를 사용해 서울 물건을 수집하고, 매각과 임대를 처분 방식으로 구분하는 구조를 확인했다. 물건 용도에 따라 집·상가·오피스로 나누고 토지·공장·창고 및 지식산업센터는 수집 범위에서 제외하는 기준을 정리했다. 공매 진행 상태는 공고와 같은 상태 코드로 관리한다.

테스트용 DB에서 실제 수집 결과와 정제 결과를 확인했다.

| 확인 항목 | 결과 |
| --- | ---: |
| API에서 읽은 건수 | 5,922건 |
| 처리·저장한 건수 | 5,419건 |
| 중복을 제외한 고유 물건 | 1,865건 |
| ID·용도·상태·좌표·지역 오류 | 0건 |

검증 후 임시 테스트 DB와 볼륨은 삭제했고, 공유 개발 DB는 유지했다.

입찰 종료일이 지났다는 이유만으로 모든 물건을 마감 처리하면 안 된다는 점도 확인했다. 실제 응답에서 수의계약이 가능한 물건은 입찰 종료일이 지난 뒤에도 계약 가능 상태일 수 있었다. 따라서 종료일만 보지 말고 온비드의 진행 상태와 수의계약 가능 여부를 함께 판단해야 한다. 목록에서 사라진 물건의 마감 처리도 이번 수집 회차의 기준 시각과 비교하도록 정리했다.

#### 2. Nginx가 배포에서 맡는 위치를 구체화했다

인프라 아키텍처는 역할에 따라 EC2 세 대를 나누는 구조로 정리했다.

| 서버 | 주요 역할 |
| --- | --- |
| Web EC2 | 외부 HTTPS 진입점, Nginx, React 정적 파일 제공, Spring Boot API 프록시, Redis |
| Data·AI EC2 | Spring Batch 데이터 수집, 공고 상태 변경, 별도 AI 서비스와 문서 처리 |
| DB EC2 | Oracle 업무·공간 데이터와 PostgreSQL 문서 벡터 저장소 운영 |

Nginx는 Web EC2에서 80·443 요청을 받고 HTTPS 인증서와 React 정적 파일을 제공한다. API 경로는 Spring Boot로 전달하고, Web에서 내부 AI 앱으로 요청을 중계한다. Data·AI 서버와 DB 서버는 외부에서 직접 접근하지 않고 내부 통신만 허용한다.

배포 흐름은 GitHub PR·병합 후 GitHub Actions가 빌드와 테스트를 수행하고, 컨테이너 이미지를 GHCR에 올린 뒤 EC2의 Docker Compose가 이미지를 받아 서비스를 실행하는 방식이다. 이 흐름에서 Nginx는 빌드 도구가 아니라 사용자의 웹 요청을 안전하게 받고 프론트엔드와 API로 나누는 운영 진입점이다.

#### 3. Oracle과 PostgreSQL의 데이터 역할을 분리했다

업무 데이터와 공간 데이터는 Oracle Database 21c에서 관리하고, 공고문 문서 벡터는 PostgreSQL과 pgvector에 분리 저장하는 구조를 아키텍처에 표시했다. Spring AI의 PgVectorStore를 이용해 문서 임베딩을 저장하고 검색하며, AI 앱 계정만 벡터 DB에 접근하도록 연결 경계를 나눴다.

Oracle의 Spatial 기능은 건물·공매·주변 시설의 공간 조회에 사용하고, PostgreSQL은 RAG 문서 벡터 전용으로 둔다. 데이터 성격에 맞춰 저장소를 분리하면 업무 트랜잭션과 문서 유사도 검색의 접근 권한과 운영 책임을 구분할 수 있다.

#### 4. 공고문 처리를 Spring Boot의 Java 기술 스택으로 표현했다

공고문은 별도 Python·LibreOffice 서비스가 아니라 Spring Boot 기반 문서 처리 흐름으로 표시했다. PDF는 PDFBox로 텍스트와 페이지를 처리하고, 표 추출에는 Tabula-java, 스캔 문서 OCR에는 Tess4J와 Tesseract를 사용한다. HWP·HWPX는 hwplib·hwpxlib로 파싱하는 구성을 적었다. 추출한 조건은 Spring AI가 초안을 만들고 관리자가 승인한 뒤 Java 규칙 엔진이 판정한다.

AI 서비스는 메인 검색·맞춤 추천과 고객상담으로 나눴다. 메인 AI는 Tool Calling으로 추천·자격·일정 기능을 호출하고, 고객상담 AI는 안내 문서 RAG를 통해 답변한다. 두 흐름 모두 Spring Boot 안에서 Spring AI와 OpenAI API를 연결하는 구조다.

#### 5. 기획서와 아키텍처 자료의 표기 차이를 확인했다

오늘 폴더에 저장된 아키텍처 PNG에는 Oracle Database 21c, PostgreSQL·pgvector, Spring Boot 문서 처리 라이브러리와 Nginx 배포 흐름이 반영돼 있다. 그러나 같은 폴더의 기획서 본문에는 `Oracle 21c XE`, Python 보조 처리, LibreOffice 표기가 여전히 남아 있다. 확정한 기술 방향과 문서 본문이 일치하도록 해당 문구를 후속 정리해야 한다.

온비드 범위와 매각·임대 구분, 용도 분류와 상태 기준도 기획서에 반영돼 있다. 다만 아키텍처 그림만 갱신하고 끝내지 말고, 기술 스택·배포 서버·문서 처리 설명이 서로 같은 기준을 가리키는지 함께 확인해야 한다.

#### 핵심 정리

- 온비드 데이터는 API 수집 건수뿐 아니라 중복 제거, 용도 분류, 상태, 좌표와 지역까지 확인해야 한다.
- 입찰 종료일이 지나도 수의계약이 가능한 물건이 있으므로 종료일만으로 마감 상태를 확정하지 않는다.
- Nginx는 외부 HTTPS 진입, 정적 프론트엔드 제공, API 프록시를 담당하며 데이터·AI·DB 서버는 내부 통신으로 분리한다.
- Oracle은 업무·공간 데이터, PostgreSQL·pgvector는 문서 벡터를 맡도록 저장소 역할을 나눈다.
- PDF·HWP 공고문 처리, AI 초안 생성, 관리자 승인, Java 규칙 판정의 책임과 순서를 아키텍처에 나타낸다.
- 기획서와 아키텍처의 기술 표기가 다르면 구현 기준도 흔들릴 수 있으므로 자료 간 일치 여부를 확인해야 한다.

실제 API 결과를 테스트 DB에 넣어 확인하면서 수집 성공 여부와 사용자에게 보여 줄 상태의 정확성은 별개의 검증이라는 점을 배웠다. 온비드처럼 수의계약이 가능한 데이터에서는 날짜 하나만으로 마감을 판정하면 유효한 물건을 숨길 수 있다. 원천 상태와 업무 규칙을 함께 해석하고, 전체 수집이 끝난 뒤 ID·용도·좌표·지역까지 확인해야 한다.

아키텍처를 구체화할 때도 기술 이름을 나열하는 것보다 요청이 어디로 들어와 어떤 서버와 저장소를 거치는지 연결을 보여 주는 일이 중요했다. Nginx의 역할과 Oracle·PostgreSQL의 책임을 구분하니 배포 흐름과 데이터 경계가 더 명확해졌다. 다만 오늘 폴더의 기획서 본문에는 아키텍처와 다른 기술 표기가 남아 있어, 구현 전에 두 자료를 같은 확정 기준으로 맞출 필요가 있다.
