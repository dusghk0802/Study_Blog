#### 1. 로그인 후 마지막으로 구경한 예매 화면으로 이동하는 문제

- 회원가입·로그인 후 마이페이지가 아니라 **마지막으로 구경한 영화 예매 화면**으로 이동하는 버그 발생 (캐시를 지우면 마이페이지로 이동)

| 원인 | 내용 |
| --- | --- |
| 자동 저장 | `useBookingPage.js`의 `useEffect`가 화면을 볼 때마다 `rememberBooking()`으로 주소를 `sessionStorage`에 저장 |
| 삭제 없음 | `bookingReturn()`은 저장된 주소를 꺼내기만 하고 지우지 않음 |
| 이동 코드 | 로그인·소셜 콜백·취향 설정·`RouteGuard`가 모두 `bookingReturn() \|\| PAGE_PATHS.profile`로 이동 |

- 원하는 동작은 **예매 화면에서 바로 로그인·가입하면 그 화면으로 복귀, 다른 화면에서 로그인하면 복귀하지 않음**
- 해결 방향 : 저장은 그대로 두고, 예매 화면을 **떠날 때(cleanup)** 가는 곳이 로그인·회원가입이 아니면 저장된 주소를 삭제
  - 로그인·가입 페이지와 공용 `state.js`는 수정하지 않고 예매 쪽 `useBookingPage.js`만 수정
- 프로젝트가 **해시 라우터(`#/login`)** 를 쓰고 있어 `window.location.pathname`으로는 이동 위치를 알 수 없음을 확인 → 해시 주소 대응 후 커밋하기로 보류

#### 2. 로그인 후 기본 이동 위치를 홈으로 변경

- 일반적인 사이트는 **이전 화면이 있으면 그곳으로, 없으면 홈으로** 이동하고, 마이페이지로 보내는 경우는 드묾
- `navigation.js`의 `redirectPage()`를 확인해 `'profile'`은 **로그인한 사용자가 로그인·회원가입·콜백·취향 설정 페이지에 있을 때만** 반환된다는 것을 확인
- → 4개 파일의 `bookingReturn() || PAGE_PATHS.profile`을 `PAGE_PATHS.home`으로 변경
- 홈에서 회원가입하면 마이페이지로 가던 원인은 가입 직후 로그인 상태가 되면서 `RouteGuard`가 돌려보낸 것이었음

#### 3. main을 받은 뒤 소셜 로그인 404

- main을 받아온 뒤 소셜 로그인 버튼을 누르면 `/oauth2/authorization/google`에서 **Whitelabel 404** 발생
- 원인 : 배포 담당 팀원이 소셜 설정을 `#---` + `spring.config.activate.on-profile=oauth-google`처럼 **프로필 조건 아래로** 옮김 → 프로필을 켜지 않으면 설정 자체를 읽지 않음
- 병합 실수가 아니라 배포 환경에 맞춘 의도된 변경이었고, 로컬 실행 방법이 공유되지 않은 상황
- → 공용 파일은 건드리지 않고 IntelliJ 실행 설정의 **Active profiles**에 `oauth-google,oauth-naver,oauth-kakao` 추가
  - 켠 프로필의 키가 `.env`에 없으면 서버가 시작되지 않으므로 키가 있는 소셜만 추가

#### 4. 취소표 대기번호가 발급되지 않는 문제 조사

- 스마트예매가 매진으로 실패했는데 **대기 신청 버튼이 나오지 않음**
- 대기 관련 코드를 찾아가며 역할을 정리

| 파일 | 역할 |
| --- | --- |
| `WaitingQueueService` | 차례가 된 사람에게 5분 예매 기회 부여, 만료 처리 (발급 아님) |
| `BookingWaitingService` | 대기번호 발급(`register`), 대기 가능 회차 목록(`choices`) 생성 |
| `BookingWaitingDispatcher` / `Worker` | 3초마다 빈 좌석을 대기 순서대로 배정 |

- 대기 가능 회차 목록은 **그룹 상태가 `ACTIVE`일 때만** 만들어지고, `validate()`를 통과한 회차만 포함됨
- 대기 기능은 Redis를 쓰지 않아 배포 환경 문제 가능성은 낮음
- 다음 단계 : 개발자 도구 Network 탭에서 `groupStatus`와 `choices` 값을 확인해 원인을 확정하고 담당 팀원에게 전달

#### 5. 선호 좌석 6개 필수 선택으로 규칙 변경

- 회원가입 후 취향 설정과 선호 정보 수정에서 **선호 좌석 6곳을 모두 선택해야 저장**되도록 변경
- 두 화면이 같은 컴포넌트(`ResidencePreference`)와 같은 API(`PATCH /api/users/me`)를 써서 한 곳 수정으로 모두 적용
- 경고 방식은 기존 극장 3곳 규칙과 맞춰 **6개 미만이면 저장 버튼 비활성화 + 버튼 옆에 "(현재 N/6)" 경고 표시**로 결정

| 구분 | 변경 내용 |
| --- | --- |
| 프론트 | `canSave` 조건을 `selectedSeats.length === 6`으로 변경, 버튼을 `save-preference-row`로 감싸 경고 추가 |
| 서버 검증 | `UserUpdateRequest`의 `preferredSeatPositions`에 `@Size(min = 6, max = 6)` 추가 |
| 서비스 | `UserService.replaceSeats()`의 1~6개 검사를 6개로 통일 |
| 테스트 | 6개 좌석 회원(`allSeats`)으로 렌더링하도록 수정 |

- `ApiExceptionHandler`가 검증 실패 시 **첫 번째 오류 메시지를 그대로** 프론트에 보내서 별도 수정 불필요
- `@Size`는 **값이 `null`이면 검사하지 않아**, 닉네임만 수정하는 요청 등에는 영향이 없음 (`@NotNull`은 붙이지 않음)
- `userApi.update` 사용처를 검색해 다른 화면에서 좌석을 함께 보내는 곳이 없는지 확인

#### 6. k6 부하 테스트

- k6는 가상 사용자(VU)가 API를 반복 호출하게 만들어 서버가 얼마나 버티는지 측정하는 도구
- 설치 : `winget install k6 --source winget` → IntelliJ 재시작 → `k6 version` 확인
- 프론트(5173)를 거치면 Vite 개발 서버가 먼저 병목이 되므로 **백엔드(8080)를 직접** 호출
- 계정 정보는 파일에 적지 않고 `-e LOGIN_ID`, `-e PASSWORD`로 전달 (`__ENV.USERS || 100`은 명령어 값이 없을 때만 쓰는 기본값)

| 스크립트 | 시나리오 |
| --- | --- |
| `main-chart.js` | 메인 차트 조회 (`/api/main`) |
| `login.js` | 로그인 → 토큰으로 내 정보 조회 |
| `browse.js` | 메인 화면 구경 + 일부 로그인 혼합 |
| `login-spike.js` | USERS명이 SPREAD초 안에 몰려 1번씩 로그인 |

- **메인 차트 조회**

| 동시 사용자 | 총 요청 | 평균 | p(95) | 실패율 |
| --- | --- | --- | --- | --- |
| 1 | 10 | 7.97ms | 10.88ms | 0% |
| 100 | 9,010 | 6.05ms | 10.61ms | 0% |

- **로그인 + 내 정보 (1명)** : 로그인 평균 133.64ms, 내 정보 평균 8.3ms → 비밀번호 해시(BCrypt)가 일부러 느리게 설계되어 로그인이 약 15배 느림
- **동시 로그인 스파이크**

| 동시 로그인 | 몰리는 시간 | 성공 | 실패율 | med | p(95) | max |
| --- | --- | --- | --- | --- | --- | --- |
| 1000 | 동시 | 204 | 79.6% | - | 1.76s | 1.84s |
| 1000 | 5초 | 1000 | 0% | 2.27s | 4.46s | 4.73s |
| 5000 | 10초 | 5000 | 0% | 17.58s | 33.63s | 35.39s |
| 5000 | 45초 | 5000 | 0% | 1.08s | 1.68s | 3.41s |
| 5000 | 60초 | 5000 | 0% | 0.088s | 14.02s | 16.56s |

- 로그인 처리량은 조건과 관계없이 **초당 약 105~110건**으로 일정 → 병목은 BCrypt의 CPU 연산
- 처리량으로 대기 시간을 예측할 수 있음 : 5000명 ÷ 110건 ≈ 45초 → 10초 집중 시 마지막 사용자 대기 약 35초 예측, 실제 35.39초
- 1000명이 **같은 순간**에 몰리면 연결 대기열이 넘쳐 대량 거절되지만, **몇 초에 걸쳐** 몰리면 전원 성공
- 60초 분산은 계산상 대기가 거의 없어야 하는데 일부가 13~16초 대기 → 일시적인 PC 자원 부족 등으로 추정, 45초 재측정에서는 재현되지 않음

#### 9. Troubleshooting

- `Whitelabel Error Page 404` (`/oauth2/authorization/google`) → 소셜 설정이 프로필 조건 아래에 있어 읽히지 않음 → 실행 설정에 Active profiles 추가
- CSS 문법 오류 → "찾을 곳" 블록의 `@media` 첫 두 줄을 대체하지 않고 추가해 중괄호가 닫히지 않음 → 중복된 2줄 삭제
- GitHub Actions `expected true to be false` (`preferences.integration.test.jsx`) → 테스트 회원의 좌석이 2개라 새 규칙에 막힘, 로컬에서 **다른 파일 이름으로 실행**해 실패를 못 잡음 → 테스트 수정 후 `npx vitest run`으로 전체 확인
- k6 `connectex: actively refused` (전부 실패) → 백엔드가 꺼져 있거나 켜지는 중 → `Started SmartTicketingApplication` 확인 후 실행
- PowerShell `'Tomcat' 용어가 cmdlet ... 인식되지 않습니다` → 로그에서 찾을 문장을 터미널에 입력함 → 로그는 **Run 창(Alt + 4)** 에서 Ctrl + F로 검색
- k6 로그인 100% 실패 (약 8ms) → 예시 값(`loadtest01`)을 그대로 넣어 없는 계정으로 요청 → 실제 테스트 계정으로 실행, 특수문자가 있는 비밀번호는 `'PASSWORD=...'`처럼 작은따옴표로 감쌈
- 동시 로그인 시 `actively refused`로 약 80% 실패 → 같은 순간에 연결이 몰려 연결 대기열(기본 약 100) 초과 → `SPREAD`로 몇 초에 걸쳐 몰리게 변경
- SPREAD를 줬는데 실행 시간이 1초대 → 스크립트에 `sleep` 수정이 저장되지 않음 → `running` 시간이 SPREAD 이상인지로 적용 여부 확인
- 체크 이름이 `로그인 5000`으로 표시 → 사람 수를 바꾸다 이름표까지 바뀜 → `r.status === 200`은 **HTTP 상태 코드(성공)** 라 사람 수와 무관하며 200으로 고정

#### 10. 핵심 정리

- 화면 간 이동 정보를 저장할 때는 **언제 저장하고 언제 지울지**를 함께 설계해야 오래된 값이 남지 않음
- main을 받은 뒤 동작이 바뀌면 병합 실수로 단정하기 전에 **파일 기록(Show History)** 으로 의도된 변경인지 먼저 확인
- 입력값 검증은 화면과 서버 **양쪽에** 두고, 서버 검증 메시지가 그대로 화면에 전달되는 구조인지 확인
- 테스트는 **실제 파일 이름으로 실행**해야 하며, 로컬에서 통과를 확인한 뒤 올려야 CI 실패를 막을 수 있음
- 부하 테스트는 숫자만 보는 것이 아니라 **처리량으로 결과를 설명할 수 있어야** 의미가 있음

로그인 후 이동 버그를 고치면서, 주소를 저장하는 코드만 있고 지우는 코드가 없으면 사용자가 의도하지 않은 화면으로 이동하게 된다는 것을 알게 되었다. 또 main을 받은 뒤 소셜 로그인이 안 되는 문제를 겪으며, 팀원의 변경이 내 로컬 환경에 어떤 영향을 주는지 확인하고 실행 방법을 공유하는 것도 협업의 일부라는 것을 느꼈다.
</br>선호 좌석 규칙을 바꾸는 작업에서는 화면만 고치는 것이 아니라 서버 검증, 서비스 코드, 테스트까지 함께 맞춰야 한다는 것을 배웠고, 테스트 파일 이름을 잘못 알아 CI가 실패한 경험을 통해 로컬에서 전체 테스트를 돌려보는 습관이 필요하다는 것을 깨달았다.

k6로 처음 부하 테스트를 해보면서, 같은 5000명이라도 몰리는 시간에 따라 결과가 크게 달라지고 로그인 처리량 하나로 대기 시간을 예측할 수 있다는 점이 가장 인상 깊었다.
</br>다음에는 해시 주소에 맞춰 예매 화면 주소 삭제 코드를 마무리하고, 대기번호가 발급되지 않는 원인을 확정해 담당 팀원에게 전달할 예정이다.
