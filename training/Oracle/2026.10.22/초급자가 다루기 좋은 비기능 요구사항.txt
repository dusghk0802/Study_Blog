백업/복구 정책

초급자가 처음부터 Redis, Kafka, Kubernetes 같은 해결책을 찿는 것은 오히려 좋지 않을 수 있습니다. 
문제 → 원인 → 증거 → 해결책의 순서를 배우게 하는 것이 중요합니다.
예를 들어 AI에게 바로

“게시판 성능을 좋게 만들어줘.”
라고 하기보다,

1단계 — 문제를 수치화합니다.
“게시글이 10만 건일 때 목록 조회가 3초 걸린다. 목표는 1초 이내다.”

이렇게 하면 단순한 “빠르게 만들어주세요”가 아니라
현재 3초 → 목표 1초 이하
라는 비기능 요구사항이 됩니다.
2단계 — AI에게 원인 후보를 찾게 합니다.

“Spring Boot + MyBatis + Oracle 게시판에서 목록 조회가 3초 걸린다. 가능한 원인을 DB, Backend, 
Network 관점에서 나누어 알려줘.”

AI가 Full Table Scan, 인덱스 부족, 불필요한 JOIN, SELECT *, 과도한 데이터 반환, N+1 형태의 추가 조회 
등을 제시할 수 있습니다.

여기서 중요한 것은 AI가 말한 것을 바로 적용하지 않는 것입니다.

3단계 — 개발자가 증거를 찾습니다.

AI 가설
   ↓
SQL 실행시간 확인
   ↓
실행계획 확인
   ↓
애플리케이션 로그 확인
   ↓
Network 응답시간 확인

예를 들어 실행계획에서 실제로 Full Table Scan이 발견됐다면 그때 인덱스를 검토합니다.
4단계 — AI에게 해결 방법을 여러 개 요구합니다.

“이 문제를 해결할 방법을 3가지 제시하고 각각 장점, 단점, 적용 난이도와 검증 방법을 알려줘.”

그러면 초급자가 AI의 첫 번째 답을 정답으로 받아들이는 습관에서 벗어나게 됩니다.
5단계 — 가장 중요한 것은 해결 후 재측정입니다.

개선 전
100,000건 → 3.1초

인덱스 적용
       ↓
개선 후
100,000건 → 0.4초

이제 학생은 단순히 “인덱스를 추가했다”가 아니라,

“10만 건 기준 3.1초였던 조회를 실행계획을 분석하여 인덱스를 적용했고, 동일 조건에서 0.4초로 개선했다.”

라고 설명할 수 있습니다.

보안도 같은 방식으로

기능 요구사항이

“회원은 자신의 게시글을 수정할 수 있다.”

라면 AI에게 “이 기능에서 발생할 수 있는 보안 문제를 찾아줘”라고 합니다.

AI가 예를 들어 다른 사용자의 게시글 ID를 바꿔 수정하는 상황을 제시하면 학생은 실제로 테스트합니다.

PUT /api/posts/100
Authorization: User-B

100번 글 작성자가 User-A인데 User-B가 수정할 수 있다면 문제가 확인된 것입니다.

그다음에야 서버 측에서

로그인 사용자
     ↓
게시글 작성자 확인
     ↓
일치?
 ┌───┴────┐
YES       NO
 ↓         ↓
수정      403

같은 해결책을 구현합니다.
Spring Security 코드 자체보다 “왜 서버에서 권한을 다시 확인해야 하는가?”입니다.

그래서 초급자의 AI 활용 프로세스를 하나로 통일할 수 있습니다

수업에서 모든 비기능 요구사항을 다음 7단계로 반복시키겠습니다.

기능 구현 
→ AI에게 위험/문제점 발견 요청 
→ 비기능 요구사항 수치화 
→ AI에게 원인 가설 요청 
→ 개발자가 로그·SQL·테스트로 검증 
→ AI에게 해결 대안 비교 요청 → 구현 후 재측정
“Redis를 사용했습니다.”

라고 발표하는 것보다

문제: 조회 요청 증가로 DB 부하 발생
측정: 동일 데이터 반복 조회가 전체 조회의 70%
AI 활용: 캐시·DB 인덱스·쿼리 개선 세 가지 대안 분석
판단: 반복 조회 특성을 고려하여 캐시 선택
구현: Redis + TTL 적용
검증: 적용 전/후 응답시간과 DB 조회 횟수 비교

라고 발표
초급자 프로젝트에서는 모든 비기능 요구사항을 다루기보다 성능 + 보안 + 안정성 + 데이터 검증 + 로그/운영 
정도의 5개 영역을 필수로 잡는 것이 적절합니다.
