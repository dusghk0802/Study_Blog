# 폴링 · 롱폴링 · SSE · WebSocket 정리

서버의 변화를 클라이언트에 **실시간으로 전달**하는 4가지 방식이다.

HTTP는 원래 **클라이언트가 요청해야만 서버가 응답**하는 구조이므로, 서버가 먼저 "새 글이 생겼어"라고 알려 주려면 아래 방법 중 하나가 필요하다.

---

## 1. 폴링 (Polling)

### 개념

클라이언트가 **정해진 간격마다** 서버에 "새 데이터 있어?"라고 계속 물어보는 방식

```
클라이언트 ──요청──▶ 서버  "새 글 있어?"  → "없어"
   (3초 후)
클라이언트 ──요청──▶ 서버  "새 글 있어?"  → "없어"
   (3초 후)
클라이언트 ──요청──▶ 서버  "새 글 있어?"  → "1건 있어"
```

```javascript
setInterval(() => fetch("/api/posts").then(...), 3000);
```

### 장단점

| 장점 | 단점 |
| --- | --- |
| 구현이 가장 쉬움 | 새 데이터가 없어도 계속 요청 → 낭비가 큼 |
| 일반 HTTP라 어떤 환경에서도 동작 | 간격만큼 알림이 늦음 |

### 주의점

- **간격 조절** : 간격이 짧으면 서버 부하가 커지고, 길면 실시간성이 떨어진다.
- **사용자 수** : 사용자가 늘면 요청 수도 그대로 늘어난다 (1,000명이 1초마다 요청하면 초당 1,000건).
- **변경분만 조회** : "마지막으로 받은 번호 이후"만 요청해 응답 크기를 줄인다.
- **종료 조건** : 작업이 끝나면 `clearInterval`로 반드시 멈춘다. 화면을 벗어나도 계속 요청하는 실수가 흔하다.

### 실무에서 자주 쓰는 경우

결과가 언제 끝날지 모르는 작업의 상태를 가끔 확인할 때, 몇 초에서 몇십 초 정도 늦어도 괜찮을 때

### 사례

1. **결제·주문 상태 확인** : 가상계좌나 외부 결제를 진행한 뒤 "입금 완료됐나?"를 몇 초 간격으로 조회하고, 완료되면 폴링을 멈추고 완료 화면으로 넘어간다.
2. **대용량 작업 진행 상태** : 엑셀 다운로드 파일 생성, 동영상 인코딩처럼 오래 걸리는 작업을 요청하면 서버가 작업 번호를 먼저 주고, 클라이언트는 그 번호로 "완료됐나?"를 주기적으로 확인한다. 관리자 대시보드 통계를 30초나 1분마다 새로고침하는 것도 같은 방식이다.

## 2. 롱폴링 (Long Polling)

### 개념

클라이언트가 요청을 보내면 서버가 **새 데이터가 생길 때까지 응답을 보류**했다가 생기면 응답하고, 클라이언트는 응답을 받자마자 다시 요청하는 방식

```
클라이언트 ──요청──▶ 서버  (응답을 붙잡고 대기 ...)
                     새 글 생김!
클라이언트 ◀──응답── 서버  "1건 있어"
클라이언트 ──요청──▶ 서버  (다시 대기 ...)
```

Spring에서는 `DeferredResult`로 구현한다.

### 장단점

| 장점 | 단점 |
| --- | --- |
| 데이터가 생기는 즉시 응답 → 폴링보다 빠름 | 응답마다 연결을 다시 맺음 |
| 쓸데없는 요청이 줄어듦 | 대기하는 동안 연결을 붙잡고 있음 |

### 주의점

- **타임아웃** : 서버, 프록시, 로드밸런서의 타임아웃(보통 30~60초)에 걸리면 연결이 끊기므로, 그 전에 빈 응답을 돌려보내고 다시 요청하게 해야 한다.
- **데이터 유실** : 응답을 받고 다시 요청하기 전 짧은 틈에 생긴 데이터를 놓칠 수 있으므로 마지막 번호 기준으로 다시 조회한다.
- **잦은 변경** : 데이터가 자주 바뀌면 사실상 폴링과 비슷해져 효과가 줄어든다.

### 실무에서 자주 쓰는 경우

WebSocket이나 SSE를 쓸 수 없는 환경(오래된 브라우저, 사내망 프록시 제한)에서 실시간에 가깝게 받아야 할 때, 서버를 따로 열지 않고 외부 서비스의 이벤트를 받아야 할 때

### 사례

1. **메신저 봇 업데이트 수신** : 텔레그램 Bot API의 `getUpdates`는 롱폴링을 지원해서, 웹훅용 공개 서버가 없는 개발 환경에서도 요청을 걸어 두고 새 메시지가 오면 바로 받을 수 있다.
2. **WebSocket 대체 경로** : SockJS 같은 라이브러리는 WebSocket이 막힌 환경에서 자동으로 롱폴링으로 바꿔 연결한다. 사내망 그룹웨어의 알림·채팅이 이런 대체 경로로 동작하는 경우가 많다.

## 3. SSE (Server-Sent Events)

### 개념

클라이언트가 연결을 한 번 열어 두면 **서버가 그 연결로 데이터를 계속 흘려보내는** 방식 (**서버 → 클라이언트 단방향**)

```
클라이언트 ──연결 요청──▶ 서버
클라이언트 ◀── 이벤트 ── 서버  "새 글 1"
클라이언트 ◀── 이벤트 ── 서버  "새 글 2"
          (연결 유지)
```

```javascript
const es = new EventSource("/api/subscribe");
es.onmessage = (e) => console.log(e.data);
```

Spring에서는 `SseEmitter`를 사용하고, 응답 형식은 `text/event-stream`이다.

### 장단점

| 장점 | 단점 |
| --- | --- |
| HTTP 기반이라 구현이 간단함 | 단방향이라 클라이언트가 보낼 때는 별도의 HTTP 요청 필요 |
| 끊기면 브라우저가 **자동 재연결**, `Last-Event-ID`로 놓친 이벤트 이어받기 | 텍스트만 전송 가능 |

### 주의점

- **연결 수 제한** : HTTP/1.1에서는 브라우저가 도메인당 동시 연결을 **6개**로 제한해 탭을 여러 개 열면 막힐 수 있으므로 HTTP/2를 권장한다.
- **서버 리소스** : 연결마다 서버 리소스를 붙잡고 있으므로 접속자가 많으면 비동기 처리나 WebFlux를 고려한다.
- **연결 정리** : `SseEmitter`의 타임아웃을 설정하고, 끊긴 연결은 목록에서 지워야 메모리 누수가 생기지 않는다.
- **프록시 버퍼링** : Nginx 같은 프록시가 응답을 모았다가 보내면 실시간으로 오지 않으므로 버퍼링을 꺼야 한다.
- **첫 이벤트** : 연결 직후 아무 이벤트도 보내지 않으면 일부 환경에서 연결이 끊기거나 503 에러가 나므로, 연결하자마자 더미 이벤트를 1번 보내는 것이 일반적이다.

### 실무에서 자주 쓰는 경우

서버가 알리기만 하면 되는 **알림, 피드, 진행 상황**, 결과를 조금씩 이어서 보여 줘야 하는 **스트리밍 응답**

### 사례

1. **AI 챗봇 답변 스트리밍** : ChatGPT, Claude 같은 AI 서비스의 API는 답변을 한 번에 주지 않고 생성되는 대로 조각씩 SSE로 보내서, 글자가 타이핑되듯 화면에 나타난다. Spring AI로 챗봇을 만들 때도 `Flux`나 `SseEmitter`로 이렇게 스트리밍한다.
2. **서비스 알림·주문 상태** : 쇼핑몰·배달 서비스의 "주문 접수 → 조리 중 → 배달 출발" 같은 상태 변경, 커뮤니티의 "내 글에 댓글이 달렸어요" 알림처럼 서버가 일방적으로 알려 주는 기능에 많이 쓴다.

## 4. WebSocket

### 개념

HTTP로 처음 연결한 뒤 **프로토콜을 WebSocket으로 업그레이드**하고, 그 뒤로는 연결 하나로 **서버와 클라이언트가 양방향**으로 자유롭게 주고받는 방식

```
클라이언트 ──HTTP Upgrade 요청──▶ 서버
클라이언트 ◀── 101 Switching Protocols ── 서버
클라이언트 ◀════ 양방향 메시지 ════▶ 서버
```

```javascript
const ws = new WebSocket("ws://localhost:8080/ws");
ws.onmessage = (e) => console.log(e.data);
ws.send("hello");
```

Spring에서는 `@EnableWebSocketMessageBroker`와 STOMP를 사용한다. (실습한 게시판이 이 방식)

### 장단점

| 장점 | 단점 |
| --- | --- |
| 연결 뒤에는 HTTP 헤더 없이 작은 데이터만 오감 → **가장 빠르고 효율적** | 구현과 운영이 가장 복잡함 |
| 텍스트 + 바이너리 모두 전송 가능 | 연결 상태를 서버가 직접 관리해야 함 |

### 주의점

- **재연결** : 끊겼을 때 자동 재연결이 없어서 직접 구현해야 한다. STOMP 클라이언트의 `reconnectDelay`가 이 역할을 한다.
- **서버 여러 대** : 서버마다 연결이 따로 잡혀 있어 A 서버에서 보낸 메시지가 B 서버에 연결된 사용자에게는 가지 않으므로, Redis Pub/Sub이나 RabbitMQ 같은 외부 브로커가 필요하다. (`enableSimpleBroker`는 서버 1대용)
- **차단 환경** : 일부 회사망이나 프록시는 WebSocket을 막으므로 SockJS로 대체 경로를 둔다.
- **인증과 보안** : 연결할 때 토큰 등으로 인증하고, 운영에서는 `wss://`(TLS)를 쓰며 허용할 Origin을 지정한다.
- **연결 유지** : 아무것도 보내지 않는 연결은 프록시가 끊을 수 있으므로 heartbeat(ping/pong)로 연결을 유지한다.

### 실무에서 자주 쓰는 경우

서버와 클라이언트가 **양쪽에서 자주** 주고받을 때, 지연이 **수십 ms 단위로** 중요할 때

### 사례

1. **채팅·메신저** : 슬랙 같은 업무용 메신저, 쇼핑몰 1:1 상담 채팅, 라이브 방송 채팅처럼 내가 보내고 상대가 바로 받아야 하는 기능. "입력 중..." 표시나 읽음 표시처럼 작은 메시지가 계속 오가는 데 적합하다.
2. **실시간 시세·협업** : 업비트, 바이낸스 같은 거래소는 시세와 호가 데이터를 WebSocket API로 제공한다. 구글 문서처럼 여러 명이 동시에 편집하는 서비스나 온라인 게임도 WebSocket으로 변경 사항을 즉시 주고받는다.

## 한눈에 비교

| 구분 | 폴링 | 롱폴링 | SSE | WebSocket |
| --- | --- | --- | --- | --- |
| 통신 방향 | 클라이언트 → 서버 | 클라이언트 → 서버 | **서버 → 클라이언트** | **양방향** |
| 연결 | 요청마다 새로 | 응답마다 새로 | 1개 유지 | 1개 유지 |
| 실시간성 | 낮음 (간격만큼 지연) | 높음 | 높음 | **매우 높음** |
| 서버 부하 | 높음 | 중간 | 낮음 | **가장 낮음** |
| 프로토콜 | HTTP | HTTP | HTTP | ws:// / wss:// |
| 자동 재연결 | 해당 없음 | 직접 구현 | **브라우저 지원** | 직접 구현 |
| 데이터 | 제한 없음 | 제한 없음 | 텍스트만 | 텍스트 + 바이너리 |
| 구현 난이도 | 쉬움 | 보통 | 쉬움 | 어려움 |
| Spring | `@GetMapping` | `DeferredResult` | `SseEmitter` | `@EnableWebSocketMessageBroker` |
| 대표 사례 | 결제 상태 확인, 작업 진행률 | 메신저 봇, WebSocket 대체 경로 | **AI 답변 스트리밍, 알림** | **채팅, 거래소 시세, 협업 편집** |

## 선택 기준

| 상황 | 추천 방식 |
| --- | --- |
| 양쪽이 자주 주고받는다 (채팅, 게임, 협업 편집) | **WebSocket** |
| 서버가 알리기만 한다 (알림, 주문 상태, AI 답변 스트리밍) | **SSE** |
| 몇 초에서 몇십 초 늦어도 된다 (결제 확인, 작업 상태) | **폴링** |
| SSE와 WebSocket을 쓸 수 없는 환경 | **롱폴링** |

## 실습한 게시판에 적용하면

- **지금처럼 "새 글 알림"만 보낼 때** : SSE로도 충분하고 더 간단하다.
- **댓글 실시간 입력이나 1:1 채팅으로 확장할 때** : WebSocket이 맞다.
